# Boltrig handover - 2026-07-24 (codex_empty_output: root cause found)

Scope: entirely open issue #1 from `HANDOVER-2026-07-23.md` (the
`codex_empty_output` cluster). Reproduced live on the beelink dev stack,
instrumented three previously-silent fail-closed paths, fixed one confirmed
bug, and traced the remaining symptom to its true root cause - which is
**not** the attestation layer the prior session's forensics suspected.

## What shipped (all four changes tested, `make check`-equivalent green:
2297 passed / 172 skipped, lint/architecture/structure/codex-protocol clean)

1. **`libraries/skills/ops/opbox.yaml`: narrowed `opbox.*` to 8 concrete
   verbs.** Real, 100%-reproducible bug: Opbox emplacement registered its
   full kernel MCP door under the `opbox.` namespace (**633 verbs**, confirmed
   via `select count(*) from verbs where id like 'opbox.%'`). The skill's
   wildcard grant expands against every one of them at tool-ceiling compile
   time (`runtime_resolver._compile_codex_tool_ceiling` iterates ALL
   registered verbs and keeps any `grants.permits(verb.id)` match), blowing
   through `codex_kernel_tools_phase.MAX_KERNEL_TOOLS` (128) and raising
   `CodexKernelToolsError: kernel tools exceed the attestation bound` on
   EVERY chat turn that loaded this skill - i.e. every org-admin/superadmin
   chat turn, unconditionally, degrading before a cell was even provisioned.
   Fix: grant exactly the 8 verbs the skill's own `prompt_fragment` already
   names (`opbox.matter.list/get`, `opbox.party.list/get`,
   `opbox.workflow.run.list/get`, `opbox.agenttask.ext.create/update`) plus
   `memory.*` (4 verbs) and `chat.ask_user`. Total ceiling ~13, nowhere near
   128. This alone took every affected turn from a hard, immediate
   `CodexKernelToolsError` degrade to actually reaching Codex.

2. **Logged three previously-silent fail-closed swallow points** (the prior
   session's requested next step): `model_proxy_peer_listener.py`
   (`_attest_and_deliver`'s bare `except Exception: pass`),
   `model_proxy_peer_attestation.py` (`attest()`'s handler, which
   deliberately raises a sanitized generic error to the CALLER but can safely
   log the real static reason server-side), and
   `codex_model_proxy_server.py` (`_guarded_stream`'s
   `except ToolCeilingViolation: return`). All three now `logger.warning`
   the real reason (never peer/model content - only our own static exception
   text or config-derived identifiers), with no change to any fail-closed
   behavior. Confirmed live: model-proxy peer attestation genuinely DOES fail
   intermittently (`ModelProxyPeerAttestationError: model-proxy peer
   attestation failed`, no further detail available even now - `attest()`'s
   internal capture path swallows the specific ancestry/registry cause before
   it reaches the log; a further drill-down would need logging inside
   `attest_peer_ancestry` itself). But see finding 3: this is a real, separate
   intermittent issue, NOT the primary explanation for `codex_empty_output`.

3. **Root cause of `codex_empty_output`, evidenced directly on the wire:
   GLM-4.6 (via bifrost's zai/Responses-API translation) does not call
   Codex's MCP-server-as-"namespace" tool correctly.** Reproduced with the
   `ops/opbox` skill fixed (so a real kernel-tools cell now provisions and a
   real model turn runs): bifrost's own request-log API
   (`GET http://127.0.0.1:8081/api/logs`) showed the model call completing
   with `status: success` and real token usage, followed by a SECOND
   `/v1/responses` call that bifrost's log recorded as `status: error,
   error_details: {status_code: 499, error: {type: "request_cancelled",
   message: "Request cancelled: client disconnected"}}` - the disconnect is
   OUR side (`codex_model_proxy_server.py`'s `_guarded_stream`), confirmed by
   the new logging in finding 2: `model proxy response stream truncated
   (tool ceiling): upstream returned a tool call outside the ceiling`.
   A **temporary, fully-reverted** diagnostic (logged raw response chunks to
   `/tmp/tool-ceiling-debug.log`, git-diff-verified clean afterward, git
   history has no trace of it) captured the actual function-call item Codex
   emitted for this turn:
   ```
   "type":"function_call","status":"completed","call_id":"call_...",
   "name":"mcp__boltrig","arguments":"{}"
   ```
   The model called the bare **namespace** name (`mcp__boltrig` -
   `CODEX_MCP_NAMESPACE_NAME`) with **empty arguments**, never naming or
   selecting any of the nested tools it was actually offered
   (`opbox_matter_list` etc.). `ToolCallStreamGuard._name_allowed` correctly
   rejects this (a bare `mcp__boltrig` matches neither an allowed leaf name
   nor a valid `mcp__boltrig<sep><leaf>` qualified form) - the guard is
   working as designed here, not buggy. With the guard temporarily bypassed
   for one diagnostic call, the turn proceeded further and the MODEL ITSELF
   reported the tool invocation failed ("The tool invocation I attempted
   failed, indicating either the `opbox.matter.list` verb isn't exposed in
   this phase or the control flow isn't reachable from here... I have 0
   matters to report") - i.e. even without our guard in the way, GLM's
   malformed call (`mcp__boltrig`, `{}`) can never resolve to a real verb on
   the kernel MCP side either. **This is a genuine model/gateway capability
   gap, not a boltrig code defect**: GLM-4.6 does not appear to understand
   the "one namespace tool with N nested function tools" convention Codex
   0.144.3 uses to represent an MCP server (verified in
   `codex_kernel_tools_phase.py` against the pinned binary for the OFFER
   shape; this session is the first live evidence of the CALL shape GLM
   actually produces for it).

## What this means for HANDOVER-2026-07-23's open issue #1

Supersede its framing. The "model-auth helper connects but attestation
fails, dropping the peer" theory (item 1(a)) is real and now logged (finding
2 above) but is a **separate, intermittent** issue, not the reproducible
cause of the `codex_empty_output` cluster. The reproducible cause is finding
3: GLM cannot drive Codex's MCP-namespace tool-calling convention, so ANY
kernel-tools turn that actually needs a tool degrades, deterministically,
regardless of attestation health.
