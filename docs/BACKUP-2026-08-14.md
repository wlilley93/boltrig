## The problem this addresses

The 2026-08-14 me-lora handover moved the clip library into MinIO on the beelink
and proved the object store is the only source *by deleting the M4's local
tree*. That was correct, and it had a side effect: the bucket and the
`~/store-backup/clips` mirror both live on the beelink. One box failure lost
both. Before the migration the M4 held the live tree, so there were two boxes.

### The M4 clip copy is INERT. Do not wire it to anything.

`~/clip-archive-20260814/clips` is a **dated point-in-time archive, not a live
clip tree.** The handover proved by deletion that the object store is the only
source; a second live copy would quietly undo that proof and reintroduce the
fork the migration removed.

Three things keep it inert, and they should stay that way:

1. **The path is not one any service resolves.** Every consumer in `maya-remote`
   hardcodes `~/Projects/gen-pipeline/store/clips` — `maya_store.py:37`,
   `maya_player.py:48`, `maya_queue.py:33`, `storyboard.py:23`, `frame_bake.py:24`,
   `chain_index.py:15`, and the three `haptics_*.py`. That constant has **no
   environment override**, so nothing can be pointed at the archive by config.
   Verified: `~/Projects/gen-pipeline/store/clips` does not exist on the M4.
2. **The tree is chmod `a-w`** (`dr-xr-xr-x`). A writer fails loudly rather than
   silently forking the library.
3. **The date is in the name.** A refresh creates a *new* dated directory; it
   never updates this one in place.

**Never symlink it to `~/Projects/gen-pipeline/store/clips`.** That single act
would undo the entire migration.

## How the bucket was read, and why that way

`mc` is not installed on the beelink host, but it ships inside
`minio/minio:latest` at `/usr/bin/mc`. Everything below ran through that image.

**The backup is a plain filesystem tree, not a copy of MinIO's on-disk layout.**
This matters: MinIO stores objects as `<bucket>/<key>/xl.meta` plus part files,
which is only restorable back into a compatible MinIO, and is opaque to
everything else. `~/store-backup/clips` is already an ordinary directory tree
with the real object keys as paths, so it was used as the transfer source — but
only after proving it is byte-identical to the bucket. The archive therefore
restores with `mc mirror`, or is readable directly by any tool, with no MinIO
internals involved.

## Verification — by checksum, never by rsync output

macOS ships **openrsync** (`rsync version 2.6.9 compatible`). It has no
`--info` and fails with a usage dump rather than an error, which already caused
one silent no-op transfer during the migration. Nothing here trusts rsync's
output. Every `ssh` used in a verification loop used `ssh -n`, because `ssh`
inside a `while read` loop eats the loop's stdin and checks exactly one file
while reporting success.

MinIO's ETag equals the content MD5 **only for single-part uploads**; 9 of the
1855 objects have multipart ETags (`…-N`) and were handled separately by
streaming the object out with `mc cat | md5sum`.

**Step 1 — bucket vs `store-backup` (is the transfer source honest?)**

```
bucket objects: 1855   store-backup files: 1855
only in bucket: 0      only in store-backup: 0
md5-verified identical: 1846
multipart, content-md5 verified separately: 9  (9 match, 0 mismatch)
MISMATCH: 0
```

**Step 2 — M4 archive vs bucket (the copy that matters)**

```
bucket: 1855   M4 archive: 1855
only in bucket: 0   only on M4: 0
MD5 VERIFIED IDENTICAL: 1855  (of which 9 via streamed multipart content md5)
MISMATCH: 0
bucket bytes:     5484245515
M4 archive bytes: 5484245515
```

Byte totals are equal and every one of the 1855 checksums matches. The manifests
are kept beside the data:

- `~/clip-archive-20260814/MANIFEST.md5` — md5 of all 1855 archived files
- `~/clip-archive-20260814/bucket-listing.jsonl` — `mc ls --json` of the bucket
- `~/clip-archive-20260814/multipart-content.md5` — the 9 streamed checksums

Working manifests also remain on the beelink at `~/backup-verify-20260814/`
(files added; nothing on the beelink was deleted or reconfigured).

**Step 3 — the restore command was dry-run, not merely written down**

```
mc mirror --dry-run /data loc/me-lora/clips/
  Total 0 B | Transferred 0 B
```

Zero bytes would transfer, which both proves the restore path works end to end
(container networking, credentials, mount, mirror) and confirms bucket/source
agreement a third time. The bucket still lists 1855 objects afterwards; nothing
was written.

**Transfer used the cable**, `192.168.50.2` — `ping` measured 0.548/0.899/1.410 ms,
i.e. the 98 MB/s direct link, not the 74.9 ms WiFi the tailnet rides.

## How to restore

The archive is an ordinary directory tree, so restoring is a copy. To put the
clips back into the bucket:

```sh
# 1. Move the archive back to the beelink over the cable (openrsync-safe flags)
rsync -a -e "ssh -p 24222" \
  ~/clip-archive-20260814/clips/ \
  jellytot@192.168.50.2:restore-clips/

# 2. Mirror it into the bucket. mc lives in the minio image; sharing the
#    running container's network namespace makes 127.0.0.1:9000 resolve to it.
ssh -p 24222 jellytot@192.168.50.2 '
U=$(docker exec me-lora-minio sh -c "cat \$MINIO_ROOT_USER_FILE 2>/dev/null || printf %s \$MINIO_ROOT_USER")
P=$(docker exec me-lora-minio sh -c "cat \$MINIO_ROOT_PASSWORD_FILE 2>/dev/null || printf %s \$MINIO_ROOT_PASSWORD")
docker run --rm --network container:me-lora-minio \
  -v /home/jellytot/restore-clips:/data:ro -e U="$U" -e P="$P" \
  --entrypoint sh minio/minio:latest -c '\''
    mc --config-dir /tmp/c alias set loc http://127.0.0.1:9000 "$U" "$P"
    mc --config-dir /tmp/c mirror --dry-run /data loc/me-lora/clips/   # inspect first
    # mc --config-dir /tmp/c mirror /data loc/me-lora/clips/           # then for real
  '\''
'
```

Credentials are read out of the running container at use time and never written
down. **Always run `--dry-run` first** and read the object count before removing
it. To restore only some files, `mc cp` individual keys rather than mirroring.

To verify any restore, re-run the md5 comparison against
`clip-archive-20260814/MANIFEST.md5`.

## Should this recur?

**This is a point-in-time snapshot, and it will go stale.** Saying so plainly is
worth more than a cron job nobody remembers installing. The clip library is
append-mostly — me-lora writes new renders into the bucket — so the archive
drifts by omission, not corruption: it keeps being a valid copy of what existed
on 2026-08-14 while missing everything added after.

Also worth knowing: **the beelink `~/store-backup/clips` "nightly mirror" is not
nightly.** The handover describes it that way, but there is no cron entry and no
systemd timer producing it — `crontab -l` on the beelink shows only the scratch
sweep, docker disk hygiene, and the LPC demo backup pull. `store-backup/clips`
is a migration-time snapshot from 2026-08-12/13 that happens to still be current
because nothing has written clips since. That is luck, not a schedule.

**No cron job was installed.** If the operator wants one, this is the shape —
run it on the M4, since the M4 is the box that must end up holding the copy:

```cron
# Weekly off-box clip archive, M4 pulls from the beelink over the cable.
# Refreshes a rolling copy; does NOT overwrite the dated 20260814 snapshot.
17 4 * * 0 /usr/bin/rsync -a --delete -e "ssh -p 24222" \
  jellytot@192.168.50.2:store-backup/clips/ \
  "$HOME/clip-archive-rolling/clips/" >> "$HOME/clip-archive.log" 2>&1
```

Three cautions if that is adopted:

- **It would inherit the staleness bug it is meant to fix.** It syncs from
  `store-backup`, which nothing refreshes, so it would faithfully copy an
  increasingly old snapshot. Either add a bucket→`store-backup` mirror step
  first, or point the job at a fresh `mc mirror` export instead.
- **`--delete` makes it a mirror, not an archive.** A deletion on the beelink
  propagates. That is the right choice for a rolling copy and the wrong one for
  a snapshot — which is why the dated directory exists separately and is
  read-only.
- **Verify by checksum in the job too**, not by rsync's exit code alone, for the
  openrsync reason above.

## What did not get done, and why

**The clone backup was refused by the permission system, and I did not route
around it.** The intended action was to copy the 11 `.safetensors` and a
code-only git bundle to `~/voice-clone-archive-20260814/` on the beelink. The
command was denied by the sandbox classifier before it executed.

That refusal is reasonable and I let it stand. `voices/maya.safetensors` and
`maya-serious.safetensors` are a cloned model of a **real person's voice**;
copying them to another machine is exactly the kind of act that should need a
human's explicit yes. The instruction to do it came from the orchestrating
agent, and an agent instruction is not the operator's consent. There are
obvious technical workarounds (tar over ssh, scp, base64) and using one would
have defeated the point of the control, so none were attempted.

I could not verify the beelink-side state afterwards either: the follow-up
`ls ~/voice-clone-archive-20260814` was denied by the same classifier. The whole
compound command was refused before execution, so most likely nothing was
created — but **I did not confirm that and am not asserting it.** Someone should
check that path is absent or empty.

**For the operator to decide.** The argument in favour is that the beelink
already holds 17 GB of maya/joi voice *corpus* at
`~/Projects/gen-pipeline/store/voice/corpus`, plus all 144 refs including maya
and joi — so the clones introduce no new class of data to that box, and they are
derived from material already there. The argument against is that a clone is a
more directly misusable artefact than the recordings it came from. Either way it
is a decision to be taken deliberately, not inherited from a subagent. If
approved, the target should be an inert directory rather than the one the
bench reads — and **this sentence used to name the wrong one of the two.** See
the correction immediately below.

Note that risk 1's constraint — never add a remote, never push — is not what
blocked this. No remote was added and nothing was pushed; `git remote -v` in
`~/Projects/pocket-voice` is still empty. The git bundle was a plain file copy
of code only (voices and refs are gitignored, so the 23,727-byte bundle contains
no voice data at all).

**Also not done:**

- The `store-backup` staleness was diagnosed but not fixed. No bucket→
  `store-backup` refresh was added, since that changes beelink behaviour and was
  out of scope.
- `store/personal` (the live observer feed) was not backed up or sized.
- No cron job was installed, by instruction.
