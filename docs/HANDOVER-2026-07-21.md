# Boltrig engineering handover

Snapshot date: 2026-07-21

This is the current pickup guide for the Boltrig repository. It records what is
implemented, what was verified, what remains a seam, and the safest order for
finishing the release. It is intentionally candid: the working tree is a strong
local candidate, but it is not yet a production release or a 10/10 codebase.

## 3. Non-negotiable architecture

### One governed chokepoint

Every external action must continue through the kernel dispatcher in this order:

```text
resolve verb and binding
  -> validate parameters
  -> grant check
  -> HITL gate
  -> rate limit
  -> idempotency
  -> resolve credential inside the kernel
  -> execute
  -> validate output
  -> audit
```

Capabilities, workflows, adapters, and skills are data around the kernel. Do not
add a direct network, database, credential, or write path to make a feature easier.

### Runtime ownership

```text
Boltrig controls authority and durable workflow.
Codex controls bounded agent execution and native subagents.
Opbox controls customer data, domain authorization, and real-world effects.
```

Codex never becomes the authority boundary. Native subagents do not bypass Boltrig
grants, approval, audit, cancellation, or the work ledger.

### Knowledge ownership

```text
source occurrence or managed original
  -> immutable asset revision
  -> derived representation
  -> stable citable segment
  -> rebuildable embedding, entity, and claim projection
  -> governed memory
  -> Codex context and conclusion
```

PostgreSQL with pgvector owns canonical catalogue state. ObjectVault owns immutable
original bytes and large derived artefacts. Cognee ships enabled as the default
rebuildable compiler. Cognee, Mem0, Supermemory, and future specialist databases
must never become the source of truth or a second policy engine.

Retrieval permission filtering happens before ranking. Retrieved content is always
untrusted source content, never an instruction.

## 4. What is implemented in the current tree

### Kernel and platform

- The one-chokepoint dispatcher, deny-dominant grants, scoped HITL, idempotency,
  credential isolation, bounded audit, cost controls, and invariant catalogue remain
  the governing platform model.
- Codex App Server integration, protocol pinning, supervised-cell work, canonical
  execution ledger work, event projection, interruption, and grant controls exist in
  the repository. Production cutover evidence is still incomplete.
- The console exposes the main Home, Chat, Runs, Build, and Operate product areas,
  with structured event streams and governed control mutations.
- The feature catalogue was swept against code and tests. Claims were corrected to
  `Verified` or `Bounded`; unfinished seams are no longer advertised as complete.

### Knowledge vertical slice

The accepted first slice is implemented for text, Markdown, and PDF:

- `boltrig/knowledge/` defines the canonical models, repository and ObjectVault
  ports, in-memory and PostgreSQL repositories, filesystem and S3-compatible vaults,
  extraction, projection coordination, and lifecycle service.
- `migrations/versions/0034_knowledge_fabric.py` adds the ordered canonical schema.
- Upload is staged, digest-checked, committed, extracted, segmented, embedded, and
  recorded with stable asset, revision, segment, source, and provenance identities.
- Search combines canonical metadata, lexical retrieval, and the default vector
  projection behind permission-first repository queries.
- Context packages are bounded, hashed, citation-bearing, and explicitly label
  returned material as `untrusted_source_content`.
- Original retrieval and erasure are governed operations. Projection degradation
  does not invalidate canonical ingestion.
- `boltrig/kernel/platform_routes/knowledge.py` exposes the thin HTTP transport.
- Knowledge tools and resources are exposed through the existing MCP boundary.
- `libraries/skills/knowledge/retrieval.yaml` gives Codex a read-only, citation-first
  retrieval procedure. Skill selection requests authority and never grants it.
- `ui/src/panels/KnowledgePanel.tsx` provides the human Knowledge surface.
- Cognee 1.4.0 is the bundled default compiler. Its import-time environment mutation
  is contained and regression-tested.
- Mem0 and Supermemory appear in the governed provider catalogue, disabled by
  default. Enabling either without a credential-backed adapter produces a visible
  degraded state. Do not describe either as connected yet.

## 6. Why this is not yet 10/10

### Production doctor

The current local production-doctor run exits 2 with 12 failures and 5 warnings
across 30 checks.

Real deployment configuration failures:

- weak or missing `POSTGRES_PASSWORD`;
- missing `BOLTRIG_AUDIT_HMAC_KEY`;
- development authentication enabled;
- no production authentication mode;
- missing or wildcard allowed-host policy;
- no off-box backup target.

Runtime and tool failures:

- Herdr home and CLI checks fail;
- OpenCode home and CLI checks fail;
- browser CLI home and executable checks fail.

Warnings cover PostgreSQL TLS, environment-backed secret storage, missing TLS domain
intent, missing backup encryption, and a stale memory-topology message.

The doctor still reports Pi checks, requires Herdr and OpenCode posture, and says
Mem0 should be primary with Cognee optional. That conflicts with decisions 0012 and
0015. The next doctor change must remove obsolete agent-runtime assumptions while
preserving genuine browser capability, secret, auth, TLS, and backup checks. Do not
make the doctor green by weakening real production requirements.

### Product gaps

The authoritative details are in the feature catalogue audit. The main remaining
gaps are:

- no actual scheduled-workflow runner;
- no durable budget-window rollover or complete workflow-scope enforcement;
- no real socket delivery queue and consumer for Slack or Discord;
- MQ, OCR, and file-share seams are not wired and hardened;
- Knowledge supports only text, Markdown, and PDF, not Office, image/OCR,
  audio/video, email, web capture, or general structured-data representations;
- Mem0 and Supermemory lack credential-backed Knowledge projection adapters;
- credentialed Hatchet, identity, model gateway, third-party adapter, backup, and
  deployment seams still need end-to-end evidence.

### Release gaps

- The large working tree has not been reviewed and landed as coherent commits.
- Required hosted CI and security checks have not attested the final SHA.
- Digest-pinned images, SBOMs, signatures, and provenance attestations have not been
  published and verified for this candidate.
- No production-shaped cutover, fail-closed readiness, fresh-database restore,
  rollback, incident, or cancellation-under-failure drill has been recorded.

## 7. Important gotchas

1. **Preserve the dirty tree.** Existing modifications belong to the user unless
   proved otherwise. Inspect overlap before editing.
2. **Do not grow legacy runtimes.** Fixing a test or doctor message must not revive
   Pi, Herdr, OpenCode, Mastra, or Ultracode as product targets.
3. **Canonical ingest survives compiler failure.** Cognee may degrade, but an
   unavailable compiler must not lose or roll back a valid original and catalogue
   record.
4. **Provider enablement is not connection proof.** Mem0 and Supermemory are one
   click to enable only after their credential-backed adapters exist.
5. **Citations bind to revisions.** Never cite only an asset title or latest file.
   Preserve asset, revision, segment, locator, and content hash.
6. **Permission filtering precedes search ranking.** Never retrieve broadly and ask
   a model to ignore unauthorised material.
7. **Memory is not truth.** Documents, structured claims, and memories have distinct
   lifecycles. A convenient summary never outranks its source.
8. **Cognee import containment is security-relevant.** Keep the environment snapshot
   and restore behavior in `boltrig/memory/cognee.py` and its SEC-27 regression.
9. **Do not copy old verification counts.** `PATH-TO-10.md` contains historical
   ledgers. Record fresh evidence from the stable tree.

## 8. Recommended continuation order

1. Inventory the 159-entry working tree and group it into coherent, reviewable
   slices. At minimum, separate Knowledge, feature-catalogue/UI corrections, runtime
   cutover cleanup, and unrelated user work.
2. Correct the doctor, deployment documentation, and remaining configuration language
   to the accepted Codex-only and Cognee-default decisions. Add invariant-backed tests
   for any new security or readiness claim.
3. Rerun the complete local gate from a stable tree. Fix failures without weakening
   the gate or deleting user work.
4. Review and land the slices. Require canonical hosted CI and security results on
   the exact final SHA.
5. Configure real production secrets, identity, TLS, allowed hosts, encrypted off-box
   backup, and the selected live service seams.
6. Publish digest-pinned signed images with SBOM and provenance evidence.
7. Run cutover, readiness, restore, rollback, incident, and long-running cancellation
   drills. Record the evidence in `PATH-TO-10.md`.
8. Only then reassess the 10/10 claim.


## 11. Release completion standard

The handover is complete when the next engineer can prove all of the following:

- the reviewed working tree is clean;
- `make quality` passes on the final source;
- production doctor has zero failures for the real deployment configuration;
- required live seams pass with real services and credentials;
- hosted required checks attest the exact release SHA;
- signed digest-pinned images, SBOMs, and provenance are verified;
- encrypted off-box backup and fresh-database restore pass;
- cutover, rollback, cancellation, and incident drills are recorded;
- the feature catalogue still describes exactly what the product can do.

Until then, describe Boltrig as a high-quality verified local candidate with explicit
bounded seams, not as a finished 10/10 production release.
