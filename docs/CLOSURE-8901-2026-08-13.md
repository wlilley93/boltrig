# Closure: the unauthenticated Maya player on beelink :8901

**Date:** 2026-08-13
**Box:** beelink (`jellytot@192.168.50.2 -p 24222`) — the *shared* build box, not beelink-prod.
**Status:** CLOSED and verified from the M4 as a tailnet peer.

---

## 1. What was open

`maya_player.py` served the Maya remote UI and its whole API with **no authentication of
its own**, and it was published straight to the tailnet:

```
tailscale serve --https=8901 http://192.168.50.2:8901
```

Every device on the tailnet — including `hanna-windows` — could fetch, with no
credentials at all:

| path | what it is |
| --- | --- |
| `/remote` | the full player UI, 62152 bytes, `<title>Maya</title>` |
| `/api/state` | player state |
| `/api/awareness` | presence / "is he here" |
| `/api/memory` | the fact sheet |
| `/api/vigil` | vigil photographs |
| `/haptics.js` | haptics client |
| `/media/*`, `/stills/*`, `/lines/*`, `/voice/*`, `/exports/*` | clips, stills, renders |

Verified before closure, from the M4:

```
$ curl https://beelink.tailb4b671.ts.net:8901/remote
HTTP 200, 62152 bytes, no credentials sent
```

The diary, fact sheet and vigil photographs were **not** being returned in full — but only
because the presence bridge on beelink is broken, so those endpoints answer
`{"withheld": true, "reason": "no presence detector"}`. **A broken component was the only
thing standing between the tailnet and personal data.** That is not a control. Closing the
port had to happen before anything repaired presence.

## 2. What changed

### a. The tailnet mount was removed

```
sudo tailscale serve --https=8901 off
```

No other mount was touched. The eight remaining mounts (`:445`, `:3000`, `:8000`, `:8088`,
`:10000`, `:18000`, `:19001`, and the two root vhosts) are exactly as they were.

### b. The player was rebound to loopback

It was already a systemd **user** unit — `~/.config/systemd/user/maya-player.service`,
`enabled`, with `Linger=yes` on `jellytot`, so it already survived reboot. (Earlier recon
said it had no unit and was hand-started; that was wrong. The giveaway is
`SYSTEMD_EXEC_PID` / `MEMORY_PRESSURE_WATCH=.../maya-player.service/` in the process
environment.) No new unit was needed — the existing one was edited:

```diff
-ExecStart=%h/.../python maya_player.py --host 192.168.50.2 --port 8901
+ExecStart=%h/.../python maya_player.py --host 127.0.0.1     --port 8901
```

The comment block above `ExecStart` was rewritten to record *why* loopback, so the next
person does not "helpfully" rebind it to the cable again.

Result — beelink now has **no non-loopback backend for the player at all**:

```
$ ss -ltnp | grep 8901
LISTEN 0 5 127.0.0.1:8901 0.0.0.0:*  users:(("python",pid=2520834,fd=3))
```

### c. The intranet proxy upstream followed it

`/home/jellytot/intranet.py` line 60:

```diff
-PLAYER = "http://192.168.50.2:8901"
+PLAYER = "http://127.0.0.1:8901"
```

The gate itself was **not** changed. The player branch in `do_GET` still reuses the exact
`authed()` / `note_fail()` / `client_key()` / `deny()` pattern that `/logs` uses. There is
no second gate and no new token scheme.

### d. Files backed up before editing

| backup | of |
| --- | --- |
| `/home/jellytot/.config/systemd/user/maya-player.service.bak-pre-loopback-20260813` | the unit |
| `/home/jellytot/intranet.py.bak-pre-loopback-20260813` | the intranet |
| `/home/jellytot/intranet.py.bak-pre-remote-proxy` | pre-proxy state (earlier phase) |

Both services restarted cleanly; `systemctl is-active` = `active` for
`beelink-intranet` and `--user maya-player.service`, journals clean, no tracebacks.

## 5. Rollback

Undo in reverse order. Nothing here needs a rebuild.

```bash
# 1. put the player back on the cable address
cp /home/jellytot/.config/systemd/user/maya-player.service.bak-pre-loopback-20260813 \
   /home/jellytot/.config/systemd/user/maya-player.service
systemctl --user daemon-reload && systemctl --user restart maya-player.service

# 2. point the intranet proxy back at the cable address
cp /home/jellytot/intranet.py.bak-pre-loopback-20260813 /home/jellytot/intranet.py
sudo systemctl restart beelink-intranet

# 3. re-publish the raw player to the tailnet  <-- REOPENS THE HOLE. Don't.
sudo tailscale serve --bg --https=8901 http://192.168.50.2:8901

# 4. remove the proxy entirely (back to before this whole workstream)
cp /home/jellytot/intranet.py.bak-pre-remote-proxy /home/jellytot/intranet.py
sudo systemctl restart beelink-intranet
```

Every `tailscale serve` edit needs `sudo` now that a unix-socket mount exists.

## 6. Residual risk and traps

- **The fail-throttle punishes a bad credential hard.** `/remote` pulls ~10 sub-resources,
  and each 403 calls `note_fail()`. `MAX_FAILS=5` means a client with an absent or wrong
  credential locks its key out for 300s from a *single page load*. Worse, a request that
  arrives while already locked out still calls `note_fail()`, so a polling client holds
  itself out indefinitely. `FAILS` is in memory —
  `sudo systemctl restart beelink-intranet` clears it. (The no-credential probes in this
  document locked out the M4's cable key; the tailnet identity path was unaffected.)
- **Presence remains broken** and is the next piece of work. It must now be repaired
  *behind* the gate — the endpoints it feeds are the diary, fact sheet and vigil
  photographs.
- **The player OOM-killed once** (15G peak, 4.9G swap) at 16:39 UTC before this work.
  `Restart=always` caught it. Unrelated to this closure, but worth watching on an 18GB
  shared box.
- **Not touched:** beelink-prod, Salad, Cloudflare R2, and every other serve mount.
