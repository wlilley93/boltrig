## What it carried

[2026] VJS-COUNTY 8 D7's forced password rotation, the half of that order that was
never built. See the commit and
`docs/GOAL-claims-must-be-load-bearing.md`; the short version is that
`validate_password_strength` stops a WEAK seed password and does nothing about a
PROVISIONING one surviving as the live credential.

## This roll carried a schema change, which the last three did not

`EXPECTED_ALEMBIC_HEAD` moved to `0039_user_must_change_password`, and the
readiness check compares heads by STRICT EQUALITY. So there is no ordering that
has no window: migrate first and the old kernel (expecting 0038) fails closed at
503; roll first and the new kernel (expecting 0039) fails closed at 503. That
second one is precisely the 2026-07-25 CV outage - forty minutes of 503 while
`docker ps` said healthy.

So the recorded recipe was followed rather than improvised, per stack:

1. `stop kernel fleet-worker` - postgres stays up
2. apply the migration
3. `up -d` on the new pinned digest

That trades a few seconds of connection-refused for never having a container that
is RUNNING and answering 503. `app.boltrig.io` went first as the rehearsal for the
client tenant.

## The migration is additive, and existing users are the proof

`ADD COLUMN IF NOT EXISTS must_change_password BOOLEAN NOT NULL DEFAULT FALSE`,
guarded by `to_regclass`. Every existing row backfills FALSE, which is the whole
safety argument: D7 is about the SEEDING flow, and a retroactive flag would have
locked the live operator out of both production consoles for a hazard their
account does not have.

Verified after each roll by reading the actual rows, not by reasoning about the
default: both tenants' only user comes back `f`. The clamp is live and clamps
nobody, which is exactly right until the next `boltrig initiate`.

## Backups, and a rehearsal that caught a silent no-op

Both databases dumped to `~/Backups/pre-0039/` BEFORE anything was touched, and
the client dump was RESTORED into a throwaway database and compared - 99 tables,
users and conversations matching the live counts. A dump nobody has restored is
not a backup.

The migration was then rehearsed against that restored copy, and the rehearsal is
what earned its keep. The first attempt ran the SQL through an `ssh "... <<'SQL'"`
heredoc, reported **exit 0**, and applied NOTHING - `alembic_version` still read
`0038` and the column did not exist. Had that been the live database and had I
trusted the exit code, the roll would have proceeded onto an unmigrated schema and
reproduced the outage this whole recipe exists to prevent.

Fixed by writing the SQL to a file and running `psql -f`. The rule is the one this
repository keeps relearning in new costumes: **check the state, not the exit
code.** That is now three distinct forms of it in three days (a masked build
failure, a masked push guard, and this).

## Not carried

`boltrig-ui` stays at `0.3.9` - no console change in this batch. The
change-password surface has no UI yet: the route exists and is tested, and the
clamp returns a distinct `password_change_required` 403 for a console to route on,
but nothing renders it. That is not a gap in the roll, it is the next piece of
work, and it only matters at the next tenant provisioning.
