# Rolling both prod boltrig stacks to 0.3.1 - what actually bites

Date: 2026-07-25
Status: DONE. `app.boltrig.io` and the CV tenant both run
`ghcr.io/wlilley93/boltrig-{kernel,fleet,ui}:0.3.1` (digest-pinned) on schema
`0037_secure_input`, all containers healthy.

## Starting state

| stack | image | schema | data |
| --- | --- | --- | --- |
| `boltrig` (app.boltrig.io) | locally-built `boltrig/*:0.1.0`, 6 days old | 57 tables, no `alembic_version` | 1 user, 4 work items, 47 audit rows |
| `cv-boltrig` (Classical Visas) | GHCR `0.3.0` | 98 tables, no `alembic_version` | 110 verbs, live client tenant |

Neither had ever been touched by alembic: both were bootstrapped from an
initdb-mounted `schema.sql` of their era. The current chain is 38 revisions.

## The migration is safe, and it is testable - rehearse it

Every migration is written `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT
EXISTS` precisely so it can run against a schema.sql-bootstrapped database (see
the `0020` docstring). So `alembic upgrade head` from base is the RIGHT path for
an untracked store, not a hazard - but prove it per stack rather than trust it:

1. `pg_dump` the live database.
2. Restore into a scratch DB on the dev box.
3. `alembic upgrade head` against the scratch DB.
4. Assert table count, `alembic_version`, and that row counts survived.
5. Boot the NEW kernel image against the scratch DB and hit `/readyz`.

Step 5 is the one that matters: a schema that migrates is not proof the app
runs. Both rehearsals passed (57->99 and 98->99 tables, data intact, `/readyz`
`{"status":"ready"}`), and both real runs then behaved exactly as rehearsed.

## Three things that bit, none of them the schema

**1. NEVER migrate under a running kernel.** Running the chain against CV while
its kernel was up killed it (`restarts=10`), it rebooted, re-registered its
adapters from the manifest - rewriting every verb row from the OLD image's specs
and undoing an earlier consequence recalibration - and then crash-looped because
the DB was now newer than the code. Stop `kernel` + `fleet-worker`, leave
`postgres` up, migrate, then start on the matching image. Doing that for
boltrig.io made its roll uneventful.

Silver lining worth keeping: that reboot PROVED manifest-driven adapters
re-register their VerbSpecs on boot, so on those tenants a code-side consequence
change self-applies once the new image is running (confirmed: `document.create`
and `document.update` came up HIGH from the code on both stacks, no manual
resync). See `2026-07-25-builtin-verbspec-drift.md`.

**2. `ports: []` does NOT clear an inherited publish.** Compose MERGES sequences
across files, so an override's empty list appends to nothing and the base
`${KERNEL_PORT}:8000` survives. Both stacks read the SAME
`~/Projects/boltrig/.env`, so the second one up dies with `Bind for
127.0.0.1:8628 failed: port is already allocated`. The fix is the explicit
`ports: !reset []` (compose v2.24+). The CV overlay now uses `!reset` on every
service; boltrig.io legitimately keeps its publishes.

**3. A read-only container needs a volume for every runtime home.** Both stacks
run `read_only: true` with only `/tmp` as tmpfs (`x-app-hardening`):

- CV's manifest sets `knowledge.enabled: true` with a filesystem vault and no
  `root`, so it defaulted under `$HOME` and boot died `OSError: [Errno 30]
  Read-only file system: '/home/boltrig/.local'`. Fixed with
  `BOLTRIG_KNOWLEDGE_VAULT` / `BOLTRIG_COGNEE_ROOT` pointed at named volumes.
  (boltrig.io has no `knowledge:` section, so it is default-OFF and unaffected.)
- boltrig.io's fleet-worker crash-looped on
  `mkdir: '/var/lib/boltrig/browser-cli/home/.config': Read-only file system` -
  it had never been given the `opencode` / `browser-cli` volumes the CV overlay
  already carries, because it had not been rolled since the runtimes started
  needing a home.

## Layout now

Both stacks are digest-pinned through a durable overlay beside the shared base
`~/Projects/boltrig/docker-compose.yml`:

- `~/Projects/opbox-prod/boltrig-tenants/cv/compose.override.yml`
- `~/Projects/opbox-prod/boltrig-tenants/boltrig-io.override.yml` (new - this
  stack previously served whatever was last BUILT on the box)

Backups from before the roll: `~/Backups/boltrig-prod-roll-2026-07-25/` on
jellytot-prod (both databases plus the pre-edit CV override).

**Caution for the next roll:** both compose projects share that one base file and
that one `.env`, so editing either affects BOTH stacks. The prod checkout of
`~/Projects/boltrig` is old (83ac67f) and carries local modifications; it was
deliberately NOT pulled during this roll, because doing so would swap the base
compose under a healthy client tenant mid-operation.
