## What it carries

The schema-validation ledger order (county, First Instance, 2026-07-27, on
SUBMISSION-2026-07-27-124116). The motivating fact was a live tenant: `opbox.get_matter`
failed `schema_invalid` eight times in four seconds and the audit row could not say which
field, because the ledger recorded THAT params were invalid and never WHICH.

## Verified by asking the running container, not by reading the tag

Both kernels, from inside the container:

```
readyz: ready
validate: [{'schema_path': ['required'], 'keyword': 'required'},
           {'schema_path': ['additionalProperties'], 'keyword': 'additionalProperties'}]
serialised has the secret? False
diagnosis: diagnosed missing ['matterId'] unexpected ['matter_id']
```

The last line is the whole point. `missing ['matterId'] unexpected ['matter_id']` is the diff
the case file could only guess at, derived at read time from the schema in force, and the line
above it is the constraint that makes it admissible: the instance value never entered the row.

## The one thing this roll does NOT do

It does not reach a row already written. Every `schema_invalid` row on either tenant from
before this afternoon still says only that params were invalid, and always will: migration
0023 REVOKEs UPDATE and DELETE on `event`, and post-write redaction was considered and
expressly refused in a sibling estate. This order is prevention. It is recorded as limit L3 of
the order and not as a caveat, because there is no cure and a reader should not go looking for
one.
