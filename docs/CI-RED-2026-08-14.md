## 1. The structural finding

### The hook does not run what CI runs, on four independent axes

`.githooks/pre-push` runs exactly three make targets:

```
run_gate "codex pin health"                codex-pin-health
run_gate "continuity projection"           continuity-projection
run_gate "python-quality (the target CI runs)"  quality-gate   # -> python-quality
```

CI runs ten jobs across two workflows. Coverage:

| CI job | what it actually runs | in the hook? |
| --- | --- | --- |
| `test-and-gate` | `make python-quality PY=python`, `public-product-validate`, `migration-parity`, `doctor-fixture` | **1 of 4 steps** |
| `worker-build` | `make worker-quality` | no |
| `worker-desktop-package` ×3 | `cargo test --locked`, `pnpm tauri build` | no |
| `site-build-test-lint` | `make site-quality` | no |
| `compose-validate` | `make compose-validate PY=python` | no |
| `source-security` | `make python-audit sast iac-scan PY=python`, `secret-scan`, `actionlint` | no |
| `codeql` ×3 | GitHub CodeQL, `security-extended` | no |
| `containers` ×4 | `docker build` + Trivy image scan | no |
| `quality` | aggregator, `test "<result>" = success` ×5 | n/a |
| `Security gate` | aggregator, ×3 | n/a |

So the hook covers **one of eight real CI jobs, and one of the four steps in
that job**. Measured against `make quality` — the Makefile's own "complete local
release gate", 8 prerequisites — the hook runs **one**. It also runs two targets
CI does not (`codex-pin-health`, `continuity-projection`), which is deliberate
and documented.

The hook's own preamble warns against exactly this: it says it runs
`python-quality` rather than `check` "so it cannot drift from CI again by
someone editing a second list." That is true of the *Python* leg and untrue of
everything else. `python-quality` is not "the target CI runs" — it is one of
eleven `run:` steps CI runs. The label is the load-bearing falsehood.

### But fixing the coverage would have caught none of today's four failures

This is the part worth keeping. Adding every missing target to the hook and
changing nothing else still prints `all gates green` on this exact push:

| failure | would a full-coverage hook, run as today, catch it? | why not |
| --- | --- | --- |
| A `worker-build` | **no** | `make worker-quality` on the branch tip passes — the failing test file does not exist in this tree |
| B `test-and-gate` | **no** | the hook already runs this exact target, and it passed |
| C `compose-validate` | **no** | with the default `PY=.venv/bin/python` the target passes locally |
| D desktop windows | **no** | no macOS/arm64 machine can run a `windows-2025` job |

Each needed a different axis, not more targets:

**Axis 1 — wrong commit.** Every CI job logged:

```
HEAD is now at 5346ebe4 Merge 22b508b369546f550945a7b0a12109ee349f78fd
                        into 2be23960248bc8e48e4e5ecdb8e7fb82b3fd18b5
```

`actions/checkout` on a `pull_request` event checks out `refs/pull/266/merge`,
not the branch tip. The branch is **73 ahead and 3 behind** `origin/main`:

```
$ git rev-list --left-right --count origin/main...HEAD
3	73
$ git merge-base --is-ancestor origin/main HEAD; echo $?
1
```

CI tested main-merged-into-branch. The hook tested the branch. Different trees.

**Axis 2 — wrong filesystem.** `scripts/quality-gate.sh` sets
`REPO_IN_VM="$(pwd)"` and OrbStack mounts `/Users` through, so the VM reads the
**host working tree**, untracked and gitignored files included. CI reads a clean
checkout. That is cause B.

**Axis 3 — wrong interpreter.** `PY ?= .venv/bin/python` locally; CI passes
`PY=python` on a runner with no project install. That is cause C.

**Axis 4 — wrong platform.** The hook runs on macOS or, via the VM, on
aarch64 Ubuntu. CI runs `windows-2025` and `ubuntu-24.04` x86_64. That is
cause D, and no local gate can ever reach it.

### The VM is a third environment, and it is unpinned

| | M4 host | `boltrig-vm` | CI runner |
| --- | --- | --- | --- |
| OS | macOS 15 | **Ubuntu 26.04 LTS** | **Ubuntu 24.04** |
| arch | arm64 | **aarch64** | **x86_64** |
| interpreter | `.venv/bin/python` 3.12 (macOS) | `~/boltrig-venv/bin/python` 3.12.13 | setup-python 3.12 |
| tree | working tree | **the same working tree, mounted** | clean checkout of the merge commit |
| toolchain | homebrew | hand-provisioned `apt`, nothing records it | pinned by runner label |

Two LTS releases and one architecture away from the runner. Nothing verifies
the VM's toolchain. Yesterday's `jq`-missing incident — same gate, pass on the
host, fail in the VM — is the general case, not an anomaly: `jq` is present in
both today because somebody installed it by hand, and no gate would notice if it
vanished again. `scripts/quality-gate.sh` checks four preconditions (orb on
PATH, VM exists, repo visible, interpreter executable, docker usable) and none of
them is "the toolchain matches the runner."

### No gate looks at the hook

`scripts/check_gate_coverage.py` enforces one direction — every `make quality`
prerequisite must be invoked by some workflow `run:` line — and it is good at it.
There is no gate in the other direction. Nothing asserts that the pre-push hook
covers the workflows, so the hook can shrink relative to CI indefinitely without
turning anything red. The three files that mention the hook at all are
`scripts/quality-gate.sh`, `scripts/check-release-age-exclusions.py` and
`tests/conftest.py`; none of them checks its coverage.

### D. `Worker desktop package (windows-x86_64)` — a POSIX literal in a Rust test. **Concurrent**, `f8a674b`.

Note the backslash in the path — Windows only. Product code,
`apps/worker/src-tauri/src/local_agent_protocol.rs:140`:

### Pre-existing debt this branch exposed

Not merge-blocking. Each is a hole this incident walked through.

1. **The hook's label is false.** `python-quality (the target CI runs)` names one
   of eleven CI `run:` steps. Change the string to what it runs. Free, today.
2. **No gate asserts the hook covers CI.** Extend
   `scripts/check_gate_coverage.py` with the converse direction: every make
   target invoked by a workflow `run:` is either invoked by `.githooks/pre-push`
   or listed in an explicit, reasoned out-of-scope set. Un-gateable jobs
   (`worker-desktop-package` on Windows, `containers`, `codeql`) go in that set
   *with the reason*, which turns today's silent gap into a written one.
3. **The hook gates the wrong commit.** Refuse the push when
   `git merge-base --is-ancestor origin/main HEAD` fails, or gate a throwaway
   `git merge-tree` of `origin/main`. This is the single highest-value change:
   it is the only one that catches cause A's class, and cause A is the only
   failure this session owns.
4. **The hook gates the wrong filesystem.** Run the Python leg from
   `git archive HEAD` extracted into a temp dir, so gitignored and untracked
   files cannot participate. Catches cause B's class.
5. **The hook gates the wrong interpreter.** Run at least the validator-shelling
   targets with `PY=python3` against a bare interpreter. Catches cause C's class.
6. **The VM is unpinned.** `scripts/quality-gate.sh` verifies five
   preconditions and none is "this environment resembles the runner." It is
   Ubuntu 26.04 aarch64 against the runner's 24.04 x86_64. At minimum record the
   VM's provisioning as a script in the repo so `jq` cannot go missing
   unrecorded; better, run the leg in an `ubuntu-24.04` container image.

## 4. Which failures are environmental rather than code defects

**Only E.** `Container (backup)` is a genuine, currently-real vulnerability
report against an unchanged, digest-pinned base image. The code did not change;
the world's knowledge of that code did.

What would make CI honest about it:

- **Distinguish "new CVE published" from "this PR added a vulnerable
  dependency."** The `containers` job already records a complete report with
  `exit-code: "0"` and uploads it as an artifact. The blocking step should
  compare against a baseline recorded on `main` and fail only on *new* findings
  attributable to the diff, reporting drift separately.
- **Find drift on `main`, not on someone's PR.** The security workflow's cron is
  `17 4 * * 1` — weekly, Mondays. The window between 08-10 and 08-14 is exactly
  the gap that cron cannot cover. Daily would have turned `main` red first,
  where it is nobody's merge blocker and obviously not a code regression.

D is *platform-specific* but is not environmental — it is a real defect in a
test fixture that only the Windows runner can observe. B looks environmental and
is not: the defect is a test asserting over an untracked file, and the local pass
was the wrong answer arrived at for a local reason.
