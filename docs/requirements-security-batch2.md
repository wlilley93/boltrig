further todolist - in case nankle is deployed on azure plus other security requirmeents;# Nankle — Security & Authentication Hardening, **Addendum (Batch 2)**  **Relationship to Batch 1.** This extends the Nankle Security & Authentication Hardening Specification. It does not repeat the 107 controls in families IAM / AZ / AGT / INJ / WEB / KEY / DATA / ADP / SUP / INF / DET; it adds new families and deeper controls. Where it sharpens a Batch 1 control it says so. The governance rule is unchanged: security-critical controls are pinned to tests with catalogue entries, binding-debt stays 0, and no control may be reachable around the kernel.  **Deployment context (read first).** "Pi" here is **pi-agent — the open-source agent *runtime*** (the agent loop + multi-provider LLM API), run as a sandboxed **software process on hardened Linux servers**, e.g. Linux VMs or containers inside **Azure** (AKS / ACI / App Service for Containers). It is **not** Raspberry Pi or any embedded device; there are no hardware-device concerns here. The relevant risks are software-runtime risks — a code-capable agent loop with **no permission system of its own**, a large JS/TS dependency tree, runtime self-extension (extensions/skills/templates), and session/telemetry features — plus the cloud and Linux substrate it runs on. The new families below address exactly that substrate.  Control IDs continue the domain-prefixed scheme; each is bindable as a `SEC-*` invariant. New families: **PI** (the runtime), **CLOUD** (Azure/cloud-native), **HOST** (Linux & container runtime), **CRYPTO**, **RES** (rate-limit / DoS / resource isolation), **UPLOAD** (file & spec ingestion), **APIX** (API surface & unsafe upstream consumption), **TEN** (multi-tenancy depth), **PIPE** (CI/CD & artifact integrity), **CONV** (conversation & memory), **PRIV** (privacy / compliance / provider risk), **IDP** (federation integrity & privileged access), **FOR** (forensics & detection depth), **GOV** (governance / vendor / disclosure).  ---  ## 15. The Pi Agent Runtime (software hardening)  Pi is a code-capable agent loop with no built-in permission system; by default it runs with the privileges of its host process and can self-extend at runtime. Batch 1 (AGT-06..09) established the sandbox, egress allowlist, no-native-tools, no-credentials, and chokepoint-parity rules. These add runtime-specific depth.  - **PI-01 — Disable Pi's native tool surface explicitly.** Pi's built-in Read/Write/Edit/Bash tools and inline `!` shell execution MUST be disabled in the Nankle deployment; the only tools a run sees are its granted Nankle verbs over the run-scoped MCP connection. A configuration that leaves any native tool enabled is a defect. *Threat: an injected prompt using Pi's own filesystem/shell tools entirely outside the kernel.* - **PI-02 — No runtime self-extension.** Pi's self-extension mechanisms (TypeScript Extensions, Skills, Prompt Templates, Themes loaded at runtime) MUST be disabled or restricted to a fixed, reviewed, pinned set baked into the image; the sidecar MUST NOT load extensions from a writable or network location at runtime. *Threat: arbitrary code execution and supply-chain injection via dynamically loaded extensions.* - **PI-03 — Strong isolation for model-directed execution.** Because the runtime executes actions a model chooses, isolate it more strongly than a normal service: run it in a micro-VM or syscall-filtering sandbox (gVisor, Kata, or a Firecracker micro-VM) rather than plain shared-kernel containers where the threat model warrants it; at minimum a dedicated non-root container with a read-only rootfs, full capability drop, and a strict seccomp profile. *(This is the "containerize/sandbox Pi" guidance, taken to its strongest form.)* - **PI-04 — Authenticated, isolated control channel.** The Nankle↔Pi channel (HTTP/RPC/stdio) MUST be mutually authenticated and reachable only from the kernel/fleet on an internal network; it is never exposed publicly. The run-scoped MCP token (IAM-15) is the only authority the channel conveys. - **PI-05 — Wall-clock and step caps at the runtime.** Independent of token/cost budgets, the sidecar enforces a per-run wall-clock timeout, a maximum tool-call/step count, and a maximum context size; a runaway or looping run is killed. *Threat: denial-of-wallet and infinite tool loops that token budgets alone may not bound quickly.* - **PI-06 — Session data confinement.** Pi session state (history, branches, forks, resumes) is treated as tenant/owner data: stored within the boundary, scope-isolated, encrypted at rest, and retention-bound. A run's session is never readable by another run, tenant, or user. - **PI-07 — Telemetry and session-sharing OFF.** Any Pi telemetry, usage reporting, or **session-publishing/sharing** feature (e.g. publishing sessions to an external hub) MUST be disabled. No conversation, prompt, tool result, or code ever leaves the boundary through a runtime feature. *Threat: silent data exfiltration via a "share your session" convenience.* - **PI-08 — Model-key confinement and provider pinning.** Pi receives only the key for its pinned model endpoint; BYOK/subscription-login paths that could introduce other credentials or providers are disabled. The provider and model are fixed by Nankle config, not selectable at runtime by the agent. - **PI-09 — Pin and verify the runtime and its tree.** Pin the Pi version and its lockfile; verify integrity on build; scan its full JS/TS dependency tree (large surface) in CI (extends SUP-03); apply the same minimum-release-age and provenance rules (SUP-01/02/04). - **PI-10 — Resource quotas per run and per host.** CPU/memory/PIDs limits on the sidecar; concurrency caps so one tenant's runs cannot starve others (links TEN-03); OOM does not take down co-located services.  ---  ## 16. Cloud-Native & Azure Security  Deploying on Azure replaces several Batch 1 controls with stronger managed primitives — use them.  - **CLOUD-01 — Managed identity, not static secrets.** The application authenticates to Azure resources (Key Vault, Postgres, Storage) using a **Managed Identity / Workload Identity Federation**, not stored secrets. Each component has its own least-privilege identity. *Threat: long-lived static cloud credentials.* - **CLOUD-02 — Azure Key Vault as the secret store.** Instantiate Batch 1 KEY-01 with Key Vault (or an equivalent KMS): credential references resolve to Key Vault secrets via managed identity; Key Vault access policies/RBAC grant the app only its own secrets; soft-delete and purge-protection enabled. - **CLOUD-03 — Block the Instance Metadata Service from agent paths.** Azure IMDS (`169.254.169.254`, requiring `Metadata: true`) is a credential-theft target via SSRF. The Pi sidecar and every adapter egress path MUST be denied access to IMDS at the network layer (extends INJ-02); only the intended platform components may reach it. *Threat: SSRF → IMDS → managed-identity token theft.* - **CLOUD-04 — Private networking for data services.** PostgreSQL (Azure Database for PostgreSQL Flexible Server), Key Vault, Storage, and any cache MUST use **Private Endpoints / Private Link**, with public network access disabled; the database enforces TLS and, where possible, AAD authentication. *Threat: publicly reachable managed databases — a frequent cloud misconfiguration.* - **CLOUD-05 — Network security groups and egress control.** NSGs/Azure Firewall restrict ingress to the reverse proxy only and constrain egress to required destinations (model endpoint, IdP JWKS, approved SaaS); the sidecar's egress allowlist (AGT-07) is enforced by NSG/firewall, not only app logic. - **CLOUD-06 — Cluster/runtime hardening (AKS/ACI/App Service).** On AKS: enable network policies, pod security standards (restricted), Azure Policy for Kubernetes, workload identity (no node-pool identity sharing), and disable the dashboard; restrict the cluster API server to known networks. On ACI/App Service: private VNet integration, no public ingress except the proxy. - **CLOUD-07 — Encryption with customer-managed keys where required.** Disk and database encryption at rest is on by default; use customer-managed keys (CMK) in Key Vault for sensitive tenants; consider confidential computing for the most sensitive workloads. - **CLOUD-08 — Edge protection.** Front the app with Azure Front Door / Application Gateway **WAF** (OWASP ruleset) and Azure DDoS Protection; TLS terminates at the edge with strong policy (CRYPTO-03); the WAF complements, not replaces, app-level controls. - **CLOUD-09 — Cloud detection and posture.** Enable Microsoft Defender for Cloud, Azure Monitor, and route logs to a SIEM (Azure Sentinel or equivalent); alert on managed-identity anomalies, NSG changes, Key Vault access spikes, and public-exposure drift (extends DET-03). - **CLOUD-10 — Least-privilege cloud RBAC and drift control.** Azure RBAC follows least privilege (no `Owner`/`Contributor` for app identities); infrastructure is defined as code (Bicep/Terraform) with policy guardrails; configuration drift is detected and reconciled.  ---  ## 17. Linux Host & Container Runtime Hardening  - **HOST-01 — Hardened, minimal OS.** Linux hosts follow a CIS-style baseline: minimal packages, no unused services, hardened `sysctl`, unused kernel modules disabled, and a mandatory-access-control layer (SELinux or AppArmor) in enforcing mode. - **HOST-02 — Rootless, user-namespaced containers.** Prefer rootless container runtime and user namespaces so a container root is not host root; containers run non-root with read-only rootfs, dropped capabilities, and seccomp (extends INF-01 at the host layer). - **HOST-03 — Patch and vulnerability management.** Automated security patching for hosts and base images; images rebuilt on a cadence and on critical CVEs; image scanning gates deployment (links PIPE-04). - **HOST-04 — SSH and administrative access.** No password SSH, no direct root login; key- or certificate-based access via a bastion/jump host with just-in-time, audited elevation; management plane not exposed to the internet. - **HOST-05 — Host integrity and audit.** `auditd` and file-integrity monitoring on hosts; tamper-evident host logs shipped off-box; alert on unexpected binaries, capability changes, or new listeners. - **HOST-06 — Time and entropy.** NTP-synced clocks (extends INF-08) and a healthy entropy source for cryptographic randomness (CRYPTO-02).  ---  ## 18. Cryptography & Randomness  - **CRYPTO-01 — Approved algorithms only.** Use current, strong algorithms (e.g. SHA-256+ for hashing/the audit chain, AES-GCM or equivalent for symmetric, RSA-2048+/ECDSA P-256+ for signatures); MD5/SHA-1/DES and weak modes are forbidden for any security purpose. Confirm the audit hash chain uses an approved hash. - **CRYPTO-02 — Cryptographically secure randomness.** All tokens, nonces, session/run keys, idempotency keys, and identifiers use a CSPRNG (`secrets`/OS RNG), never `random` or predictable counters. *Threat: predictable run/MCP tokens or ids enabling guessing/forgery.* - **CRYPTO-03 — TLS policy.** TLS 1.2+ only (prefer 1.3), strong cipher suites, certificate validation always on (`verify=False` forbidden, extends DATA-01), OCSP stapling at the edge, and certificate pinning for the most critical egress (model/IdP) where feasible. - **CRYPTO-04 — Constant-time comparisons.** Secret/HMAC/token comparisons are constant-time (extends ADP-08). - **CRYPTO-05 — Key lifecycle.** Defined key rotation cadence, secure generation in the KMS/HSM, no key reuse across purposes or environments (extends KEY-05), and documented recovery/escrow that does not weaken confidentiality.  ---  ## 19. Rate Limiting, DoS & Resource Isolation  Batch 1 INF-04/AGT-04 covered per-verb/tenant limits and cost ceilings; these add connection- and flow-level depth.  - **RES-01 — Connection- and request-level limits.** Enforce request body size, header count/size, URL length, and connection timeouts at the edge and app; mitigate Slowloris/slow-read via timeouts and concurrency caps. *Threat: connection-exhaustion DoS.* - **RES-02 — Streaming limits.** Cap concurrent SSE/WebSocket streams per user/tenant, enforce idle and absolute stream timeouts, and bound buffered events (extends WEB-07). *Threat: stream-flooding resource exhaustion.* - **RES-03 — Sensitive-flow abuse protection.** High-value flows (spawn, chat, eval, adapter generation) get stricter, separately-tuned limits and abuse/anomaly detection (OWASP API6); automated/bot abuse is detected and throttled. - **RES-04 — Queue and fan-out backpressure.** The fleet/Hatchet queues enforce backpressure and bounded depth so a flood of work or recursive spawning cannot exhaust workers; spawn depth/fan-out caps (AGT-04) are the agent-side bound, queue limits the infra-side bound. - **RES-05 — Per-tenant resource quotas.** CPU, memory, concurrency, token, and cost quotas per tenant prevent a noisy or hostile tenant from degrading others (links TEN-03, PI-10). - **RES-06 — Algorithmic-complexity safety.** Inputs that drive parsing, regex, or expansion are size-bounded; no super-linear behaviour on attacker-sized input (extends INJ-07).  ---  ## 20. File & Specification Ingestion  The platform ingests OpenAPI specs (Adapter Studio), documents (file/Graph adapters), and potentially uploads — each a parser and SSRF surface.  - **UPLOAD-01 — Validate by content, not extension.** Uploaded/ingested files are validated by magic bytes and a strict allowlist of types; the client-supplied filename, extension, and `Content-Type` are never trusted; size-capped; stored outside any web root with non-executable permissions. - **UPLOAD-02 — Spec-ingestion SSRF and bomb defence.** When ingesting an OpenAPI/Swagger document by URL, the fetch obeys the egress allowlist and IMDS/internal-range blocks (INJ-02, CLOUD-03); remote `$ref` resolution to internal or arbitrary hosts is disabled; parsing is bounded against billion-laughs/deeply-nested/decompression-bomb inputs. *Threat: a malicious spec causing SSRF or a parser DoS, or generating a hostile adapter.* - **UPLOAD-03 — Generated artefact stays gated.** A spec-derived adapter remains inert until named human review (ADP-04); the rendered source is reviewed; generation introduces no dynamic code execution. - **UPLOAD-04 — Content scanning.** Where documents are ingested into memory/knowledge, scan for malware and for embedded prompt-injection payloads before they enter agent context (links CONV-02). - **UPLOAD-05 — Identifier normalisation.** Verb/noun ids, skill ids, and grant strings are Unicode-normalised and restricted to a safe character set before matching, so homoglyph/normalisation tricks cannot bypass a grant or collide with an existing id. *Threat: a look-alike verb id slipping a grant check (extends the AZ-02 wildcard-boundary rule).*  ---  ## 21. API Surface & Unsafe Upstream Consumption  Completing the OWASP API Top 10 beyond Batch 1.  - **APIX-01 — Inventory and version the surface.** All endpoints (including `/v1/mcp` and streaming) are inventoried and versioned; no debug, staging, or undocumented endpoints in production; deprecated endpoints are removed, not left reachable (OWASP API9). - **APIX-02 — Upstream responses are untrusted (OWASP API10).** Data returned by third-party APIs, SQL sources, and MCP servers is validated against the verb output schema and treated as untrusted **content** when it flows into agent context — it is a prompt-injection vector (links AGT-02). Never blindly forward or act on upstream data. - **APIX-03 — Enumeration and bulk-extraction limits.** List/search endpoints are paginated and bounded; detect and throttle mass-extraction patterns (an authorised agent or user slowly harvesting data); apply egress/DLP monitoring on high-volume reads. *Threat: data exfiltration through legitimate read verbs.* - **APIX-04 — Strict content negotiation.** Enforce expected `Content-Type`/charset on requests; reject unexpected media types; no content sniffing (links WEB-03 nosniff). - **APIX-05 — Error and response hygiene.** Uniform error shapes with no internal detail, stack traces, upstream bodies, or version leakage (extends INF-07, ADP-05).  ---  ## 22. Multi-Tenancy Isolation (depth)  - **TEN-01 — Defence-in-depth isolation.** Tenant isolation is enforced in code AND by Postgres RLS (AZ-04); a single missed predicate cannot cross tenants; isolation is tested with a hostile-tenant fixture. - **TEN-02 — Per-tenant key separation.** Consider envelope encryption with per-tenant data keys for sensitive deployments so a key compromise is tenant-scoped; the most sensitive tenants may use CMK (CLOUD-07). - **TEN-03 — Resource and concurrency isolation.** Per-tenant quotas (RES-05) and noisy-neighbour protection so one tenant cannot starve or DoS others; the sidecar concurrency caps (PI-10) apply per tenant. - **TEN-04 — Complete offboarding.** Tenant/user de-provisioning deletes or cryptographically shreds all associated data (work items, conversations, memory, audit per retention/legal-hold rules) with an audit record of the deletion (links PRIV-04). - **TEN-05 — Cross-tenant side-channel awareness.** Shared caches/embeddings/rate-limiters are keyed by tenant so timing or key-collision cannot leak across tenants.  ---  ## 23. CI/CD Pipeline & Artifact Integrity  The build/deploy pipeline is a high-value target; compromising it bypasses every runtime control.  - **PIPE-01 — Harden the pipeline.** Protected branches, required reviews on security-sensitive paths (auth, crypto, kernel, adapters), signed commits where feasible, and least-privilege CI runners; secrets in CI are short-lived and scoped. - **PIPE-02 — Keyless cloud deploy.** CI authenticates to Azure via OIDC/workload-identity federation, not stored cloud credentials (mirrors CLOUD-01 for the pipeline). - **PIPE-03 — Artifact signing and admission.** Build artefacts/images are signed (e.g. Sigstore/cosign); only signed, provenance-verified images are admitted to run (admission control); aim for a defined SLSA provenance level. - **PIPE-04 — Security gates are required and enforced.** SAST, SCA/dependency scanning, secret scanning, container/image scanning, IaC scanning, and (in staging) DAST run as **required** checks; a failing gate blocks merge/deploy. *Live gap reminder: with CI billing blocked, none of this enforces remotely — clearing it is a prerequisite (extends SUP-06).* - **PIPE-05 — Internal dependency proxy.** Pull dependencies through an internal proxy/registry with allow-listing and caching, reducing exposure to upstream registry compromise and typosquatting.  ---  ## 24. Conversation & Memory Security  The conversational and (optional) memory layers persist attacker-influenceable content across turns and sessions.  - **CONV-01 — Memory/history poisoning defence.** Content persisted from a conversation or ingested into memory is untrusted; it cannot, on later retrieval, alter an agent's grants, identity, or budget, and is kept distinguishable from instructions (extends AGT-02 across time). *Threat: an attacker seeding a thread/memory with instructions that influence a future privileged turn (OWASP LLM persistence/poisoning).* - **CONV-02 — Ingestion-time screening.** Documents and content entering memory are screened for injection payloads and malware before they become retrievable agent context (links UPLOAD-04). - **CONV-03 — Retrieval is scope- and access-controlled.** Memory/vector retrieval returns only items the requesting context is permitted to see; the vector store enforces tenant/owner scoping (no embedding-space leakage across users/tenants); cross-scope retrieval is denied and tested (extends Batch-1 memory controls). - **CONV-04 — Sensitive data in memory follows residency.** Embeddings/summaries derived from sensitive data are produced and stored only via local endpoints and within the boundary; retention and erasure apply to memory and conversations (links PRIV-04). - **CONV-05 — Conversation confidentiality.** Conversations are owner/scope-isolated and encrypted at rest; access to another user's conversation is denied; the model provider's visibility of conversation content is governed by PRIV-02.  ---  ## 25. Privacy, Compliance & Model-Provider Risk  - **PRIV-01 — Data-flow mapping and DPIA.** Maintain a data-flow map (what data reaches which adapter, model endpoint, and store) and a DPIA for processing involving personal data; purpose limitation for memory/knowledge. - **PRIV-02 — Model-provider data handling.** Use zero-data-retention / no-training contractual options with hosted model providers; treat providers and sub-processors as vendors under GOV-02; sensitive data goes only to local endpoints (AGT-11). Document what leaves the boundary to which provider. - **PRIV-03 — Audit-log access control.** The audit log contains sensitive activity; reading/exporting it is itself a privileged, scope-filtered, audited action (extends OBS/AZ-07); audit access is least-privilege. - **PRIV-04 — Retention, erasure, and legal hold.** Enforce configurable retention; support data-subject erasure across work items, conversations, memory, and (per legal-hold rules) audit, with an audit record of the erasure (links TEN-04). - **PRIV-05 — PII minimisation and pseudonymisation.** Minimise PII collection; pseudonymise/tokenise PII at rest where feasible; redaction precedes any hosted-model or external call (extends DATA-04). - **PRIV-06 — Automated-decision transparency.** Where agents make or materially influence decisions about people, retain sufficient record (via the execution tree/audit) to explain the basis, supporting "right to explanation" obligations.  ---  ## 26. Federation Integrity & Privileged Access  - **IDP-01 — Single trusted issuer per environment.** Accept tokens only from the configured issuer(s); each service validates its own audience to prevent token-audience confusion across services (extends IAM-03). - **IDP-02 — Group/claim-mapping integrity.** The IdP-group → role/scope mapping is trusted input; protect it: the mapping configuration is change-controlled and audited (links AZ-07), and roles are granted from verified claims only. Validate that a user cannot self-assign privileged groups at the IdP (an IdP-governance requirement). - **IDP-03 — Just-in-time provisioning safeguards.** If users are auto-created from token claims, validate and constrain what is provisioned; default to least privilege; no automatic elevation from claims alone. - **IDP-04 — Privileged access management.** Org-admin and break-glass accounts use stronger controls: mandatory MFA/step-up, separation of duties, time-boxed elevation, and heightened audit/alerting; break-glass use triggers an alert and review. - **IDP-05 — Lifecycle and de-provisioning propagation.** De-provisioning at the IdP promptly revokes Nankle access (short token TTL or introspection, IAM-07); dormant sessions/accounts are detected and closed.  ---  ## 27. Forensics, Canaries & Detection Depth  - **FOR-01 — Centralised, tamper-resistant logging.** Ship audit and security logs to centralised, append-only/WORM or external storage so an attacker with host access cannot erase them; the hash chain provides tamper-evidence, external storage provides tamper-resistance. - **FOR-02 — Correlation and forensic readiness.** Propagate correlation/run ids across services (the execution tree supports this); define what is captured for incident reconstruction; ensure time-stamps are trustworthy (HOST-06). - **FOR-03 — Canary tokens and honeytokens.** Plant canary credentials, canary verbs, or honeytoken records; any access triggers a high-priority alert — an early-warning tripwire for credential theft or unauthorised exploration. - **FOR-04 — Detection for agent-specific abuse.** Alert on grant-denial spikes, anomalous tool-call sequences, sidecar egress-policy violations, sudden read-volume (exfiltration), repeated HITL rejections, and unusual spawn depth/fan-out (extends DET-03 with agent signals). - **FOR-05 — Approval-integrity signals.** Detect approval fatigue/abuse: alert on bursts of approval requests, auto-deny suspicious patterns, and require deliberate confirmation (not a single click) for destructive approvals; approval cards present full context to the human (anti-social-engineering of the approver).  ---  ## 28. Governance, Vendor Risk & Disclosure  - **GOV-01 — Secure SDLC and change gates.** Threat modelling on significant changes to auth, crypto, the kernel, the agent runtime, the adapter layer, and the UI (extends DET-05); a security review gate for high-risk changes; security champions and training. - **GOV-02 — Third-party/vendor risk.** Assess and periodically re-review external dependencies as vendors: model providers, consumed MCP servers, adapter upstreams, and key libraries (data handling, security posture, sub-processors); maintain an approved-list. - **GOV-03 — Vulnerability disclosure and monitoring.** A responsible-disclosure/security-contact policy; monitor CVEs and advisories for the stack (FastAPI, Postgres, Hatchet, Pi and its JS tree, key libraries) and remediate within SLA; consider a bug-bounty as the program matures. - **GOV-04 — Configuration-drift and posture management.** Continuously verify runtime configuration against the secured baseline (IaC + policy, CLOUD-10); alert and reconcile drift; the manifest-as-source-of-truth round-trip (Round Three C1) aids this. - **GOV-05 — Periodic independent assessment.** Scheduled penetration tests and, as appropriate, third-party audits (e.g. toward SOC 2 / ISO 27001); findings tracked to closure and, where they encode a guarantee, bound as invariants.  ---  ## 29. Addendum — Definition of Done  In addition to the Batch 1 security DoD, the addendum is complete when:  1. **Pi runtime** runs with native tools, shell, runtime self-extension, telemetry, and session-sharing disabled; under strong isolation with wall-clock/step/resource caps; on an authenticated internal-only control channel; with session data confined and the runtime + JS tree pinned and scanned. 2. **Azure/cloud** uses managed identity (no static cloud secrets), Key Vault for secrets, private endpoints with public access disabled, NSG/firewall egress control with IMDS blocked from agent paths, WAF + DDoS at the edge, CMK where required, and Defender/Sentinel detection. 3. **Linux/host** follows a CIS baseline with enforcing MAC, rootless user-namespaced containers, automated patching, bastioned key-only admin access, and host integrity monitoring. 4. **Crypto** uses approved algorithms, a CSPRNG for all tokens/ids, TLS 1.2+ with validation always on and constant-time comparisons, and a defined key lifecycle. 5. **DoS/resource** enforces connection/stream/body limits, sensitive-flow throttling, queue backpressure, and per-tenant quotas. 6. **Ingestion** validates by content, defends spec-fetch SSRF and parser bombs, keeps generated artefacts gated, screens content into memory, and normalises identifiers. 7. **API** is inventoried/versioned with no debug endpoints, treats all upstream responses as untrusted content, and bounds enumeration/bulk extraction. 8. **Tenancy** enforces code+RLS isolation (hostile-tenant tested), per-tenant resource isolation, and complete offboarding. 9. **Pipeline** is hardened with keyless cloud deploy, artifact signing + admission control, and required, enforced security gates. 10. **Conversation/memory** resists poisoning across turns, screens ingestion, access-controls retrieval, and applies residency/retention. 11. **Privacy** maintains data-flow mapping/DPIA, zero-retention provider terms, privileged audit access, retention/erasure, PII minimisation, and decision transparency. 12. **Federation/PAM** trusts a single issuer per environment with per-service audience validation, integrity-controlled claim mapping, JIT safeguards, break-glass controls, and prompt de-provisioning. 13. **Forensics** ships tamper-resistant centralised logs, supports reconstruction, plants canaries, detects agent-specific abuse, and protects approval integrity. 14. **Governance** runs a secure SDLC with change gates, vendor-risk review, disclosure/CVE monitoring, drift control, and periodic independent assessment. 15. **Governance ratchet** — every security-critical control here that encodes a guarantee is invariant-bound at binding-debt 0, and the extended vibe-coding checklist (items 1–40) passes.  ---  *The center of this system — one audited chokepoint, deny-dominant grants, credential isolation, tamper-evident audit — is sound. Batch 1 completed the application perimeter; this addendum completes the **runtime, cloud, host, pipeline, and data-lifecycle** perimeter around it, with the Pi agent runtime treated for what it is: a powerful, code-capable software loop with no permission system of its own, to be sandboxed, pinned, starved of ambient authority, and never trusted with anything the kernel has not granted.*
