# Nankle — Security & Authentication Hardening Specification  **Document type:** Security architecture and requirements (defensive hardening), extending the Nankle SRS. **Audience:** engineers and reviewers shipping Nankle to production. **Posture:** zero-trust, fail-closed, defence-in-depth, least-privilege. Assume every input is hostile, every dependency is a supply-chain risk, and every agent output is attacker-controlled text.  This document is written against the real stack — Python 3.12 / FastAPI kernel, React + Vite UI, PostgreSQL, Redis, Hatchet, a Pi reasoning sidecar, and the adapter layer — and it calls out, by name, the gaps a fast-build leaves behind. Control IDs are domain-prefixed (IAM, AZ, AGT, INJ, WEB, KEY, DATA, ADP, SUP, INF, DET, VIBE) for readability; **each is bindable as a `SEC-*` invariant in the catalogue, and security-critical controls MUST be test-bound at binding-debt 0** (the existing K-29/K-30 gate).  Standards referenced: OWASP Top 10 (2021), OWASP API Security Top 10 (2023), OWASP Top 10 for LLM Applications, OWASP ASVS (target L2+; L3 for the kernel and auth), NIST SP 800-63B (authentication), NIST SP 800-53 (controls).  ---  ## 0. What this document protects, and against whom  ### Assets (in priority order) 1. **Credentials and signing keys** — adapter secrets, model API keys, JWT/JWKS keys, Hatchet tokens, at-rest keys. 2. **The dispatch chokepoint** — the integrity of grant, HITL, credential, and audit enforcement. 3. **Tenant and personal data** — work items, conversations, memory, documents, the audit log. 4. **The agent runtime boundary** — preventing an agent (or an injected prompt) from exceeding its grants. 5. **Availability and cost** — protection against DoS and LLM-cost-exhaustion.  ### Adversaries and trust boundaries - **External unauthenticated attacker** — the public edge (UI, kernel API, webhooks, the MCP face). - **Authenticated-but-malicious or compromised user** — privilege escalation, BOLA/IDOR, tenant crossing. - **Malicious content the agent reads** — indirect prompt injection from tickets, documents, emails, tool results. *This is a first-class adversary, not an edge case.* - **A compromised or malicious external service** — a poisoned MCP server, a hostile API, a rug-pulled tool definition. - **A compromised dependency** — npm/PyPI supply chain, including the Pi sidecar's large JS dependency tree. - **An insider** — a privileged operator; mitigated by least-privilege, separation of duties, and tamper-evident audit.  Trust boundaries that MUST be enforced: Internet→edge; edge→kernel; kernel→fleet; fleet→sidecar; kernel→adapters→external services; tenant↔tenant; user↔user; agent↔kernel (the agent is *outside* the trust boundary — it only acts through granted verbs).  ### Inherited principles and governance All prior principles hold; three are security-load-bearing: **P2** (the kernel is the only chokepoint — no security control may be bypassable by a side path), **P8** (least privilege by default), and **the severability condition** (no kernel/model coupling to sibling kernels). Every new guarantee is pinned to a test with a catalogue entry; binding-debt stays 0.  ---  ## 1. Identity & Authentication (Login)  The login path is the highest-value target. Current state: an `OidcVerifier` validates `iss`/`aud`/`exp`/`nbf` against a cached JWKS via authlib; subject and tenant are taken from verified claims, never from headers or the body; the system is **fail-closed** when no IdP is configured; a header-trusting `dev_principal_resolver` exists for local dev only. The controls below harden and complete that path.  ### Federation and token validation - **IAM-01 — Verified claims are the only identity source.** Tenant and subject derive solely from a cryptographically verified token. No endpoint may read identity from a request header or body. *(Built — keep it invariant-bound.)* - **IAM-02 — Explicit algorithm allowlist.** Token verification MUST pin an explicit signature-algorithm allowlist (e.g. `RS256`, `ES256`) and reject every other `alg`, especially `none` and any symmetric algorithm. Do not rely on the codec inferring the algorithm from the JWKS. *Threat: alg=none and RS256→HS256 confusion.* - **IAM-03 — Full claim validation.** Validate `iss`, `aud`, `exp`, `nbf`, and `iat`; reject tokens with no expiry; enforce a sane maximum lifetime and a bounded clock-skew leeway (≤120s). Validate `azp`/client where the IdP issues it. - **IAM-04 — Access vs ID tokens.** Accept only access tokens at the API; reject ID tokens used as access tokens (validate `token_use`/`typ` where present). *Threat: ID-token replay to call APIs.* - **IAM-05 — JWKS rotation and `kid` handling.** The JWKS cache MUST have a TTL and MUST refetch on a `kid` miss (then fail closed if still unresolved). *Gap today: the JWKS is cached for process lifetime with no rotation — key rollover would break verification or pin stale keys.* The JWKS fetch MUST verify TLS using the configured CA bundle and time out. - **IAM-06 — Replay resistance.** Where the IdP issues `jti`, reject replays within the token lifetime; prefer short-lived access tokens (≤15 min) with refresh at the IdP rather than long-lived tokens. - **IAM-07 — Revocation and logout.** Support token revocation/introspection (or short TTLs) so that logout and de-provisioning take effect promptly; a revoked or de-provisioned subject MUST lose access without a redeploy.  ### SAML (if enabled) - **IAM-08 — SAML hardening.** The SAML path is a seam today; if implemented it MUST defend against XML Signature Wrapping (validate the signed assertion is the one consumed), disable external entity resolution (XXE), validate `Conditions`/`NotOnOrAfter`/`Audience`, enforce single-use `Assertion` IDs, and require signed assertions. Treat any unsigned or partially-signed assertion as invalid.  ### The development backdoor - **IAM-09 — Dev auth is impossible in production.** The header-trusting resolver MUST be unreachable in any non-local deployment: it requires an explicit `NANKLE_DEV_AUTH=1`, and the system MUST refuse to start if dev auth is enabled together with any production signal (a configured public bind, TLS terminator, or `ENV=prod`). The reverse proxy MUST strip all `x-nankle-*` identity headers from inbound requests so they can never reach the app from outside. *Threat: the #1 rapid-build failure — a debug auth bypass left reachable.* - **IAM-10 — Fail-closed by default.** With neither a real verifier nor explicit dev auth configured, the kernel rejects all requests. *(Built — keep it.)*  ### Sessions, MFA, brute-force - **IAM-11 — MFA and password policy delegated to the IdP.** Nankle does not store passwords; MFA, password strength, lockout, and conditional access are enforced by the IdP and MUST NOT be bypassable by Nankle. Document a minimum IdP posture (MFA required for privileged roles). - **IAM-12 — Session handling.** The API is bearer-token; if any browser session cookie is introduced it MUST be `HttpOnly`, `Secure`, `SameSite=Strict` (or `Lax` with anti-CSRF, see WEB-04), scoped, and short-lived, with idle and absolute timeouts. - **IAM-13 — Authentication-failure handling.** Auth failures return `401` with no detail about why (no "user exists"/"bad signature" distinction to the client); failures are rate-limited and audited; repeated failures from a source trigger an alert (DET-03).  ### Service-to-service and run-scoped tokens - **IAM-14 — Mutually authenticated internal calls.** Kernel↔worker, kernel↔sidecar, and any service-to-service call MUST be authenticated (mTLS or signed service tokens) and MUST NOT rely on network position alone. *Zero-trust: an attacker on the internal network is assumed.* - **IAM-15 — Run-scoped MCP tokens.** The per-run token that scopes the Pi sidecar's MCP connection MUST be short-lived, audience-bound to the kernel MCP face, bound to a single run, and carry no authority beyond that run's grants. It is never logged and never reused. - **IAM-16 — Delegation integrity (on-behalf-of).** When an agent acts on behalf of a user, the delegated identity is cryptographically tied to the originating verified session; an agent cannot assert an arbitrary `on_behalf_of`. Delegated authority is the intersection of the user's permissions and the agent's grants, never their union.  ---  ## 2. Authorization & Tenancy  Current state: deny-dominant, fail-closed grants; effective authority = tenant ceiling ∩ caller grants; tenant scoping on every store query. Two real gaps from review are folded in below (AZ-05, AZ-06).  - **AZ-01 — Server-side enforcement only.** Every authorization decision is made server-side at the kernel. The UI's hiding of a control is never a security boundary. *Threat: client-side-only authz — a pervasive fast-build failure.* - **AZ-02 — Deny-dominant, fail-closed grants.** An explicit deny always wins; anything not explicitly allowed is denied; wildcards match the noun namespace only (`jira.*` ≠ `jirax.read`). No grant is `*` by default; a tenant-wide grant is an org-admin-only, audited decision. *(Built — keep it.)* - **AZ-03 — Object-level authorization on every access (anti-BOLA/IDOR).** Every read or mutation of an object addressed by id (work item, conversation, run, audit record, adapter, skill, workflow, HITL request) MUST verify the caller's tenant AND scope owns or may access that object, in the store query — never trust an id from the client. *This is OWASP API #1 and the most common fast-build hole.* - **AZ-04 — Tenant isolation with RLS.** Every query is tenant-scoped in code, and PostgreSQL Row-Level Security MUST be enabled as defence in depth so a missed `WHERE tenant_id` cannot leak across tenants. The application connects as a least-privilege role bound to its tenant context. - **AZ-05 — Department/object scope on collection endpoints.** Collection listings MUST filter by the caller's department scope, not only tenant. *Gap today: `/v1/work` filters by tenant only, so a department-scoped user can list another department's queue — fix in the store query and bind a test.* - **AZ-06 — Caller-scoped discovery.** Capability discovery MUST reflect the caller's effective grants (tenant ceiling ∩ caller scope), not the tenant ceiling alone. *Gap today: `/v1/capabilities` is tenant-scoped, leaking out-of-scope verb schemas; invoke is correctly per-caller, so this is information disclosure, not action — still close it.* - **AZ-07 — Privileged surfaces gated.** Admin, authoring (Workflow/Adapter/Skill/Router studios), evaluation, audit-export, and configuration endpoints require a permitting role; access is audited. Default-deny for any unrecognised route. - **AZ-08 — Step-up for high-consequence.** High-consequence verbs and destructive admin actions MUST require the HITL approval gate (and, where supported, IdP step-up/re-authentication). The gate is enforced in the kernel and is not bypassable by an agent. *(Gate built — extend to admin actions.)* - **AZ-09 — No privilege escalation via "test".** Skill test-spawns and eval runs execute strictly under the initiating user's grants through the full chokepoint; "preview"/"test" is never an escalation path. - **AZ-10 — TOCTOU-safe checks.** Grant, budget, and idempotency checks and the action they guard MUST be atomic with respect to concurrent requests (e.g. budget reservation before execution, single-flight on idempotency keys) so a race cannot bypass a limit. *(Reservation-before-run is built — keep it atomic.)*  ---  ## 3. Agent, LLM & MCP Security  The agent is **outside** the trust boundary. It only ever acts by calling granted verbs through the kernel; that is the entire safety model, and the prompt is *not* a security control.  ### Prompt injection (OWASP LLM01) - **AGT-01 — Grants, not prompts, are the boundary.** Defence against prompt injection (direct and indirect) rests on least-privilege grants and the HITL gate, never on instructing the model. An injected prompt cannot call a verb the run is not granted, cannot exceed depth/budget caps, and cannot execute a high-consequence verb without human approval. Security MUST NOT depend on system-prompt wording. - **AGT-02 — Untrusted content is marked and contained.** Content the agent reads from tools (tickets, documents, emails, search results, web pages) is untrusted input; it MUST NOT be able to alter the agent's tool grants, identity, or budget, and MUST be kept distinguishable from instructions in the context. Tool results are data, not commands. - **AGT-03 — Tool output is never auto-executed.** No tool/verb result is ever evaluated as code, shell, SQL, or a new instruction by the runtime or the kernel. Rendering of tool output in the UI is escaped/sanitised (WEB-01).  ### Excessive agency (OWASP LLM06/08) - **AGT-04 — Depth, fan-out, and budget caps enforced.** `max_depth`, `max_children_per_step`, `max_new_items_per_step`, and token/cost budgets are enforced in code (not just declared) with escalation on breach. *(Built — keep bound.)* - **AGT-05 — Least-privilege ephemerals.** A child's grants are exactly its skills' grants ∩ tenant ceiling; nothing ambient. *(Built.)*  ### The Pi sidecar (no built-in permission system) - **AGT-06 — Sandboxed, no native tools.** The sidecar runs containerised with no native filesystem/process/network/credential tools; the only tools a run sees are its granted verbs over a run-scoped MCP connection. *Critical: Pi by design runs with the host process's privileges — the sandbox is the control.* - **AGT-07 — Egress allowlist.** The sidecar's network egress is restricted to exactly two destinations: the kernel MCP endpoint and the configured model endpoint. No open-internet, host, or lateral access. Enforced at the container/network layer, not in app code. - **AGT-08 — No secrets to the sidecar.** The sidecar receives a model key for its pinned endpoint and a run-scoped MCP token only; verb credentials are resolved inside the kernel and never reach it. *(Specified in Round Two — enforce.)* - **AGT-09 — Chokepoint parity for MCP.** Every action from the MCP face runs the identical dispatch sequence as a direct invoke (grant, HITL, credential, audit); the MCP path adds no bypass. *(Round Two SEC-26.)*  ### MCP consumer and model endpoints - **AGT-10 — External MCP servers are untrusted.** A consumed MCP server is treated as hostile: its tool definitions are reviewed and pinned at activation (the review gate), re-validated on change (defend against tool-definition "rug pulls"), its calls run the chokepoint under grants, and its connection is egress-isolated. Never auto-trust a server's advertised tools. - **AGT-11 — Sensitive→local model routing.** Data classified sensitive is processed only by a local endpoint; a misroute to a hosted endpoint is blocked and audited. *(Model router built — keep bound.)* - **AGT-12 — Prompts carry no secrets.** Credentials, tokens, and unredacted PII are never placed in a model prompt; PII redaction sits on the egress path before any hosted call. *(PII redaction built.)* - **AGT-13 — Output handling.** Treat model output as untrusted: validate it against the verb/output schema before use; never let raw model output select a verb outside the run's grants or construct an unvalidated URL/SQL/command.  ---  ## 4. Injection & Unsafe Operations  - **INJ-01 — Parameterised SQL only.** Every SQL adapter and store query uses parameterised statements; no string-built SQL with user/agent input. Reserved identifiers are quoted (the `window` column is the live example). *Threat: SQLi via the SQL adapter or a generated query.* - **INJ-02 — SSRF defence on all outbound HTTP.** Adapter and JWKS/model HTTP calls MUST enforce an egress allowlist and block requests to link-local (`169.254.169.254` and the cloud metadata range), loopback, and RFC1918 ranges unless explicitly intended; resolve-then-pin to defeat DNS rebinding; cap redirects and validate redirect targets. *Threat: an agent-influenced or generated-adapter URL reaching cloud metadata or internal services — a top fast-build hole.* - **INJ-03 — Command/script-runtime sandboxing.** The `script` runtime MUST execute only allowlisted, parameterised commands in a sandbox with no shell interpolation of agent input, restricted filesystem and network, and resource limits. No `shell=True` on untrusted input. - **INJ-04 — Path traversal prevention.** File/document verbs canonicalise and confine paths to an allowed root; reject `..`, absolute escapes, and symlink escapes. *Threat: `document.read`/file adapter traversal.* - **INJ-05 — No insecure deserialization.** No `pickle`/`eval`/`yaml.load` on untrusted input; JSON only, parsed safely; library YAML loaded with a safe loader. JSONB is data, never executed. - **INJ-06 — Schema validation at the boundary (anti-mass-assignment).** Every request body and verb parameter set is validated against an explicit schema before use; no blind `**kwargs` spread into models or queries; unknown fields rejected, not silently bound. *(SEC-21 — keep strict.)* - **INJ-07 — ReDoS and resource safety.** Any regex over untrusted input (including the cron and webhook validators) is bounded; inputs are size-capped; pagination and result sets are bounded to prevent memory exhaustion. - **INJ-08 — Log/header injection safety.** Newlines and control characters in values are neutralised before logging; response headers are not built from unvalidated input. *(The audit log is hash-chained and scrubbed — keep it.)*  ---  ## 5. The Site (Web Application)  Current state: **the kernel app ships with no CORS policy, no security headers, and no Host validation.** A reverse proxy (Caddy) is present in the secure overlay, but these controls MUST exist explicitly and be verified (defence in depth). This is the canonical "the demo works, security headers were never added" gap.  - **WEB-01 — Output encoding / XSS prevention.** All agent output, tool results, markdown, and chat content rendered in the UI MUST be sanitised/escaped (e.g. a vetted sanitiser for any HTML/markdown; never `dangerouslySetInnerHTML` on untrusted content). *Threat: stored XSS via agent-rendered or tool-returned content — acute here because content is attacker-influenceable.* - **WEB-02 — Content-Security-Policy.** Serve a strict CSP: no `unsafe-inline`/`unsafe-eval`, nonce- or hash-based scripts, `default-src 'self'`, explicit `connect-src` for the API/SSE/WebSocket origins, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`. *Gap today.* - **WEB-03 — Security headers.** Set `Strict-Transport-Security` (long max-age, includeSubDomains, preload), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (and CSP frame-ancestors), `Referrer-Policy: no-referrer`/`strict-origin`, `Permissions-Policy` locking down powerful features, and COOP/COEP where applicable. *Gap today.* - **WEB-04 — CSRF strategy.** The API uses bearer tokens and MUST NOT accept ambient cookie credentials for state-changing requests; if any cookie auth is added, a double-submit or synchroniser anti-CSRF token plus `SameSite` is mandatory. Make the no-ambient-credential rule explicit so a future cookie does not silently open CSRF. *Threat: "it's an API so CSRF doesn't apply" — false once a browser holds a cookie.* - **WEB-05 — CORS allowlist.** CORS MUST use an explicit origin allowlist; never `*` with credentials, never reflect `Origin`. `Access-Control-Allow-Credentials` only with named origins. *Gap today: no CORS policy in the app.* - **WEB-06 — Host header / virtual-host validation.** Validate the `Host` against an allowlist (TrustedHost) to prevent host-header poisoning and cache/redirect abuse. *Gap today.* - **WEB-07 — Authenticated, origin-checked streaming.** SSE (`/v1/chat`) and any WebSocket are authenticated like every other endpoint, validate `Origin`, and enforce per-stream authorization and idle timeouts; a dropped client cannot resume another user's stream. - **WEB-08 — No secrets or source maps in the client bundle.** No API keys, tokens, or internal URLs are embedded in the frontend; production builds ship no source maps; debug tooling is stripped. - **WEB-09 — Safe redirects.** No open redirects; redirect targets are validated against an allowlist. - **WEB-10 — Clickjacking and sensitive UI.** Framing denied; sensitive actions (approvals, admin) are not embeddable; autocomplete disabled on sensitive fields.  ---  ## 6. Secrets & Key Management  Current state: the DB holds credential references only; secrets resolve inside the kernel and are scrubbed from audit; `secret_store` defaults to `env`.  - **KEY-01 — A real secret store in production.** Production MUST use an external secret manager (Vault/cloud KMS/sealed secrets), not plaintext environment variables. *Gap-risk: the `env` default is acceptable for dev only; require a managed store in prod.* - **KEY-02 — References only at rest.** The application database stores secret references, never secret values. *(Built.)* - **KEY-03 — Secrets never reach agents, logs, or the client.** Credentials never enter a prompt, a tool result, the audit detail (scrubbed), the frontend bundle, or an error message. *(Scrubbing built — keep the test that greps the audit for secret patterns.)* - **KEY-04 — Rotation without downtime.** Reference-based credentials rotate in the secret store and take effect without a redeploy; impending expiry alerts. *(Built — surface in the admin console.)* - **KEY-05 — Key hierarchy and separation.** Distinct keys per purpose (JWT/JWKS, at-rest, Hatchet tokens, model keys) and per environment; no shared secrets across dev/staging/prod. *Operational note: hatchet-lite regenerates signing keys on restart — never carry a dev Hatchet token to another environment; mint per environment.* - **KEY-06 — Short-lived internal tokens.** Service and run-scoped tokens are short-lived and narrowly audienced (IAM-14/15). - **KEY-07 — Secret scanning in CI.** A secret scanner (e.g. gitleaks) runs in CI and on pre-commit; no secret is ever committed; rotate immediately if one is. - **KEY-08 — No default or hardcoded credentials.** No hardcoded passwords/keys anywhere; default compose credentials are clearly dev-only and changed on deploy; the system refuses obvious defaults in production.  ---  ## 7. Data Protection & Privacy  - **DATA-01 — TLS in transit everywhere.** All external and service-to-service traffic is TLS; adapters to enterprise systems support mTLS; weak ciphers/protocols disabled; certificate validation never disabled (`verify=False` is forbidden). - **DATA-02 — Encryption at rest.** PostgreSQL data and backups are encrypted at rest; the secure overlay provides encrypted volumes. - **DATA-03 — Tenant and scope isolation.** Enforced in code and by RLS (AZ-04); conversations and memory are owner/scope-isolated; cross-tenant and cross-user access is denied and tested. - **DATA-04 — PII handling and classification.** PII is detected and redacted before leaving the kernel boundary; sensitive-classified data is processed only by local endpoints; data classification drives routing. *(Built.)* - **DATA-05 — Tamper-evident audit.** The audit log is append-only and hash-chained; every action (incl. denials, HITL, admin changes) is recorded with actor and on-behalf-of identity; integrity is verifiable on re-derive. *(Built — keep bound.)* - **DATA-06 — Backup security and tested restore.** Backups are encrypted, access-controlled, and restore-tested; a restore reconstitutes state and resumes in-flight runs. *(Backup/restore documented — test it.)* - **DATA-07 — Retention and erasure.** Configurable retention is enforced; support data subject erasure (GDPR) across conversations, memory, and work items where legally required, with audit of the erasure. - **DATA-08 — Data residency.** Sensitive data and its derivatives (embeddings, summaries, memory) stay within the configured boundary; the sensitive→local rules apply to memory and knowledge (Round Three SEC-31).  ---  ## 8. Adapters  Adapters are the kernel's hands; each is an egress and an injection surface.  - **ADP-01 — Least-privilege, read-scoped credentials.** An adapter's credential is the minimum scope for its verbs; read-only unless a binding requires write; per-tenant separation. - **ADP-02 — Credential confinement.** The resolved `Credential` is used only for the duration of one call inside the kernel→adapter boundary, is repr-suppressed, and is never serialised into `output`, returned to an agent, or logged. *(Built — keep the defensive `__str__`.)* - **ADP-03 — Per-adapter egress allowlist (anti-SSRF).** Each HTTP adapter is constrained to its service's hosts; INJ-02 applies. A generated adapter's base URL and any agent-supplied URL parameters are validated against the allowlist. - **ADP-04 — Generated-adapter code is reviewed and contained.** A generated adapter is inert until a named human reviews it (the review gate); the generated source is presented for review; it inherits the hardened HTTP base (timeouts, bounded retries, pagination caps) and adds no dynamic code execution. *Threat: code generation is a fast-build hotspot — never auto-activate generated code.* - **ADP-05 — Error mapping without leakage.** Native errors map to the common taxonomy; adapter errors returned to callers carry no secrets, internal hostnames, stack traces, or raw upstream bodies. - **ADP-06 — Timeouts, retries, and DoS safety.** Every adapter call has a timeout; retries use bounded exponential backoff with jitter and a cap (no amplification); responses and pagination are size-bounded. - **ADP-07 — SQL/script/file adapter safety.** SQL adapters parameterise (INJ-01); script adapters sandbox (INJ-03); file adapters confine paths (INJ-04) and cap ingested size. - **ADP-08 — Inbound webhook verification.** Webhook payloads are HMAC-verified (constant-time comparison), replay-protected (timestamp/nonce window), and schema-validated before becoming work items; an unsigned webhook is rejected unless a secret is explicitly absent by configuration. *(HMAC verification built — add replay protection.)* - **ADP-09 — MCP-consumer isolation.** A consumed MCP server's connection is egress-isolated, its tools pinned/reviewed (AGT-10), and its results run the chokepoint. - **ADP-10 — High-consequence marking.** Adapters MUST mark mutating/destructive verbs `high` so the HITL gate engages; a write verb defaulting to `low` is a defect.  ---  ## 9. Supply Chain & Build Integrity  - **SUP-01 — Pinned, hash-locked dependencies.** Python (incl. the `durable`/`inference` extras) and npm dependencies are version-pinned and hash-locked; lockfiles are the source of truth and reviewed like code. - **SUP-02 — Delay same-day releases.** Adopt a minimum-release-age policy (the Pi project's `min-release-age` pattern) to avoid pulling a freshly-compromised package; review dependency bumps explicitly. - **SUP-03 — Vulnerability and license scanning in CI.** SCA (e.g. pip-audit, npm audit/osv) runs in CI as a required check; the Pi sidecar's JS tree is scanned too (large attack surface). - **SUP-04 — SBOM and provenance.** Produce an SBOM per build; sign images; prefer reproducible builds; verify base-image provenance. - **SUP-05 — Generated and external code as supply chain.** Generated adapters (ADP-04) and consumed MCP servers (AGT-10) are treated as untrusted third-party code/config and gated by review. - **SUP-06 — The CI gate must actually run.** The invariant gate, the test suite (with Postgres), the security scans, and the UI build MUST run as **required** checks on the main branch. *Live gap: GitHub Actions is billing-blocked, so none of this currently executes remotely — clearing it is a security action, because it is what enforces every bound control and ruling condition D3.*  ---  ## 10. Infrastructure & Deployment Hardening  - **INF-01 — Hardened containers.** Run as non-root with a read-only root filesystem; drop all Linux capabilities not required; apply seccomp/AppArmor profiles; use minimal/distroless base images; set memory/CPU/pids limits on every service. - **INF-02 — Never mount the Docker socket** into any service; no service has host-level control. - **INF-03 — Network segmentation.** Only the reverse proxy/UI is internet-exposed; the kernel, workers, Postgres, Redis, Hatchet, and the sidecar are on internal networks; the sidecar's egress is allowlisted (AGT-07). Postgres/Redis are never publicly bound. - **INF-04 — Edge hardening and DoS protection.** The reverse proxy enforces TLS, request size limits, and edge rate limiting; per-verb/tenant rate limits (built) defend the kernel; budgets/hard-stops defend against LLM-cost-exhaustion DoS. - **INF-05 — Least-privilege data roles.** The application connects to PostgreSQL as a least-privilege role (no superuser, no DDL at runtime); RLS enabled (AZ-04); migrations run under a separate, controlled role (Alembic). - **INF-06 — Secrets injection, not baking.** Secrets are injected at runtime from the secret store/sealed secrets; never baked into images or committed compose files; the secure overlay terminates TLS and provides at-rest encryption. - **INF-07 — Fail-closed, no-debug production.** Debug modes, verbose tracebacks, auto-reload, and the dev auth resolver are off in production; error responses are generic (no stack traces to clients); `/healthz` reveals no internal detail. - **INF-08 — Time synchronisation.** All hosts are NTP-synced (token expiry, clock-skew, JWKS, audit ordering, and webhook replay windows depend on correct time). - **INF-09 — Environment isolation.** Dev/staging/prod are fully isolated (separate manifests, secrets, databases, Hatchet tenants); no shared credentials; no prod data in lower environments.  ---  ## 11. Detection, Logging & Response  - **DET-01 — Security event logging.** Authentication successes/failures, authorization denials, HITL decisions, admin/config changes, adapter activations, and budget breaches are logged with actor and context (the hash-chained audit covers most — ensure auth and admin events are captured). - **DET-02 — No sensitive data in logs.** Logs and audit detail are scrubbed of secrets and minimise PII (KEY-03, INJ-08). - **DET-03 — Anomaly alerting.** Alert on grant-denial spikes, authentication-failure bursts, impossible-travel, budget/cost spikes, sidecar egress-policy violations, and generated-adapter activations. - **DET-04 — Incident response and rotation playbooks.** Documented procedures for credential/key compromise (rotate via KEY-04), dependency compromise (SUP-03), and tenant-isolation incidents; a tested compliance export (DATA-05) supports investigation. - **DET-05 — Periodic security verification.** Scheduled penetration testing and a recurring threat-model review; the severability and "quarterly severability audit" pattern is mirrored for security invariants.  ---  ## 12. The "Vibe Coding" Anti-Pattern Checklist  A reviewer MUST confirm none of these fast-build failures is present. Each maps to a control above.  1. **Auth enforced only in the UI / client-side authz.** → AZ-01. Verify every endpoint enforces server-side. 2. **Missing object-level checks (BOLA/IDOR).** → AZ-03. Fetch-by-id without an ownership/scope check is the default LLM-generated CRUD bug. 3. **Debug/dev auth bypass reachable.** → IAM-09. The `x-nankle-*` header resolver must be unreachable in prod and stripped at the proxy. 4. **JWT verification weak or off.** → IAM-02/05. No `verify=False`, explicit alg allowlist, JWKS rotation. 5. **No security headers / CSP / CORS / Host validation.** → WEB-02/03/05/06. *Present-state gap in the kernel app.* 6. **XSS from rendering model/tool output.** → WEB-01. Never trust agent-influenceable content in the DOM. 7. **SSRF from agent- or generated-URL HTTP calls.** → INJ-02. Block metadata/internal ranges. 8. **String-built SQL / shell.** → INJ-01/03. Parameterise; no `shell=True` on untrusted input. 9. **Secrets in env/git/images/logs/frontend.** → KEY-01/03/07/08, WEB-08. Verification & Governance  - **VER-01 — Security controls are test-bound.** Security-critical controls are pinned to tests with catalogue entries; binding-debt stays 0. Existing bound examples to retain and extend: credential isolation (audit-scrub grep), deny-dominant/fail-closed grants (tenant-ceiling intersection), HITL gate non-bypass, tenant isolation, chokepoint parity for MCP, sidecar least-privilege, sensitive→local routing, severability. - **VER-02 — Automated security pipeline.** CI runs SAST, dependency/SCA scanning, secret scanning, container image scanning, and (in a staging environment) DAST/ZAP against the running app — as required checks (SUP-06). - **VER-03 — Manual verification.** Periodic penetration testing and threat-model review (DET-05); review the vibe-coding checklist (§12) on every significant change to auth, the adapter layer, the agent runtime, or the UI. - **VER-04 — Severability and chokepoint integrity.** The severability test (no kernel/model coupling to sibling kernels) and the single-chokepoint property are continuously enforced; no security control may be reachable around the kernel.  ---  ## 14. Definition of Done (Security)  Security hardening is complete when:  1. **Login** — token verification pins an explicit algorithm allowlist, validates `iss/aud/exp/nbf/iat`, accepts access tokens only, rotates JWKS with `kid`-miss refetch, and verifies JWKS TLS; the dev auth resolver is provably unreachable in production and stripped at the proxy; the system is fail-closed without a verifier; service-to-service and run-scoped tokens are mutually authenticated, short-lived, and least-privilege. 2. **Authorization** — every object access enforces tenant AND scope (BOLA-proof), collection endpoints (`/v1/work`) and discovery are caller-scoped, RLS is enabled, privileged surfaces are gated, and high-consequence actions require the gate — each proven by test. 3. **Agent/LLM/MCP** — grants and the HITL gate (not prompts) bound agent authority; the sidecar is sandboxed, egress-allowlisted, native-tool-free, and credential-free; MCP calls run the chokepoint; sensitive→local routing holds; consumed MCP servers are reviewed and pinned. 4. **Injection** — SQL parameterised, SSRF blocked (metadata/internal ranges), script sandboxed, paths confined, no insecure deserialization, schema-validated inputs — each tested. 5. **Site** — CSP, HSTS, nosniff, frame denial, referrer/permissions policies, an explicit CORS allowlist, Host validation, output sanitisation, and authenticated origin-checked streaming are present and verified. 6. **Secrets/Data** — a managed secret store in prod, references-only at rest, secrets absent from logs/agents/client, rotation without downtime, TLS everywhere (no `verify=False`), encryption at rest, tested encrypted backups, tamper-evident audit, retention/erasure, and data residency. 7. **Adapters** — least-privilege confined credentials, per-adapter egress allowlists, generated adapters reviewed and contained, timeouts/bounded retries, leak-free errors, verified replay-protected webhooks, and correct high-consequence marking. 8. **Supply chain/Infra** — pinned hash-locked deps with SCA/secret/image scanning and an SBOM, hardened non-root read-only containers with no Docker socket, segmented networks with an isolated egress-allowlisted sidecar, least-privilege DB roles with RLS, edge rate-limiting and cost ceilings, fail-closed no-debug production, and time sync. 9. **CI** — the invariant gate, tests (with Postgres), security scans, and UI build run as **required** checks on main (billing block cleared). 10. **Governance** — every security-critical control is invariant-bound at binding-debt 0; the vibe-coding checklist passes; severability and single-chokepoint integrity are continuously enforced.  ---  *Security is not a milestone but a property maintained under change.
