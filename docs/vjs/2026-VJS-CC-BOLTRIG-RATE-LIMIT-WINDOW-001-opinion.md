SUBMISSION-2026-07-25-170321. Clerk verdict: **stands-with-correction**, per incuriam:

## Holding

A principled third is adopted: a NARROWED AND CONDITIONAL Option B. The fixed epoch-aligned window in boltrig/kernel/ratelimit.py stays. The algorithm is not the defect. It is rate-correct over sustained time (over T windows an attacker obtains at most max*(T+1) admissions, so only the instantaneous burst doubles), and on every surface the limiter currently guards the burst doubling is immaterial: 5/min per identity against a 6-digit TOTP with a ~3-code acceptance set and a 5-minute challenge TTL (boltrig/identity/totp.py:40,58,95) yields at most roughly 55 guesses over the challenge lifetime at ~1.6e-4 success, and the channel intake bounds (120/min per channel, 30/min per sender, boltrig/kernel/channel_routes.py:66-67) are spend throttles whose sustained rate is preserved. BUT the fixed window stands only on conditions, because verification turned up a larger, undisclosed defect in the same control. The limiter's only live backend is a per-process, per-boot in-memory counter: RedisCounter (boltrig/kernel/ratelimit.py:41) is constructed NOWHERE in boltrig/ or tests/, Kernel defaults to InMemoryCounter (boltrig/kernel/__init__.py:45) and build_kernel_async never passes counter= (boltrig/api/bootstrap.py:369,379), while the module docstring (ratelimit.py:3-5) states "The production back end is Redis", docker-compose.yml:13 attributes "rate-limit + ephemeral counters" to the redis service, the kernel service depends_on redis service_healthy, and boltrig/api/readiness.py:225-241 makes Redis REQUIRED in production. The delivered bound therefore differs from the recorded bound by more than the 2x at issue, and silently multiplies by N the day anyone adds a second worker or replica. The conditions in the directives, not the choice of algorithm, are what this judgment orders.

## Ratio

Where a governed control delivers less than its configured bound, the binding question is not which algorithm is correct but whether the record states what is delivered. A bounded, deterministic shortfall that preserves the sustained rate and is immaterial on every surface the control guards may stand, but ONLY if the delivered bound is recorded at the point where the control is CONFIGURED (not merely in a test) and is pinned by a test that names the property. And the delivered bound must be read off the code that actually runs: an unwired or untested backend is not evidence of production behaviour, and may be relied on neither to establish that a control is adequate nor to cost a change to it. A backend that the record names but no production path constructs is itself the defect, because it makes the record assert a control the deployment does not have.

## Why a sliding window was refused

Option A, moving to a sliding window, is REFUSED ON THE EVIDENCE, not in principle. Both costs the case file assigned to Option A fail verification, so the refusal does not rest on them. (1) "A sliding window stores a timestamp per hit, which on a flooded public endpoint is memory amplification" is wrong for a REJECTING limiter: it need never store more than max timestamps per key, and this repo already contains exactly that bounded pattern in boltrig/adapters/http_base.py:88-118, whose deque appends only while len(self._calls) < self._max. The protocol point is accurate as far as it goes: Counter.incr(key, window_seconds) does not carry max, so it would need to. (2) "Rewriting the Redis implementation, changing production behaviour on EVERY rate-limited path" is wrong: RedisCounter is dead code, constructed nowhere and covered by no test, so rewriting it changes zero production behaviour. Option A is refused instead because on every surface the limiter guards today the shortfall is a burst doubling only, the sustained rate is preserved, and the guarded secrets and spends are not sensitive to a single doubled burst. EVIDENCE THAT WOULD CHANGE THE ANSWER AND PERMIT RENEWAL: a rate-limited surface where a SINGLE boundary burst, as distinct from the sustained rate, causes irreversible or disproportionate harm. Concretely: a hard external quota with a penalty or ban for overshoot, an account-lockout or tripwire threshold counted by this limiter, an irreversible spend where 2x a configured cap is material, or a guarded secret whose guess space is small enough that doubling the attempt budget matters. Operator telemetry showing boundary-timed bursts in the wild would also do it. On renewal the application must be argued on MATERIALITY, since the cost case did not survive verification and cannot be re-run.

## Obiter

PERSUASIVE ONLY, not part of the ratio. (1) _WINDOW_SECONDS in ratelimit.py:56 covers only 'minute' and 'hour', and enforce does _WINDOW_SECONDS.get(rl.per, 60), silently mapping an unknown per to 60 seconds. RateLimit is constructed from operator-supplied stored data with no validation of per (boltrig/kernel/registry.py:58 and boltrig/store/rows.py:55 both do RateLimit(**rl)), and the sibling RateLimitConfig.window_seconds() in adapters/http_base.py:73 DOES accept 'second'. A manifest written in the adapter vocabulary would be silently enforced 60x stricter. It fails strict rather than loose, so it is not a security hole, but two limiter vocabularies in one repo is a trap and rejecting an unknown per would be better than defaulting it. (2) RedisCounter sets EXPIRE only when count == 1 (ratelimit.py:51-52); a failed EXPIRE leaves a key with no TTL. Because window ids are monotonic the key is never reused, so this is a slow memory leak rather than a bypass. Worth fixing only if D3 is satisfied by wiring rather than by deletion. (3) The key derivation at ratelimit.py:68-69 produces f'{tenant_id}:{verb_id}:{verb_id}' for scope='verb', duplicating the verb id. Keys stay distinct so nothing is broken, but it reads as a bug and invites one. (4) Because a bounded sliding window already exists in this repo at adapters/http_base.py:88-118, a future renewal of Option A should be costed as a small in-memory change plus a protocol change to carry max, not as the memory-amplification risk the case file described. (5) The advocate's response to the CI flake, pinning the clock and adding an explicit property test rather than widening a tolerance or retrying, is the right instinct and is commended: it converted an intermittent failure into a recorded property. That instinct is precisely why the record defects in D1, D2 and D6 should be closed rather than argued.

## Clerk's corrections, and how they were taken

The clerk found no conflicting binding authority (searched: all 13 orders in
`.vjs/orders/`, the ten in-force statutes, the five judgments, and 38 canon
orders) but returned `implementable: false` with the following. Each is recorded
with what was actually done, so the order is not read as more satisfied than it
is.

- D7 CONTRADICTS THE CODE AND CANNOT DELIVER THE PROPERTY IT NAMES (material). D7's guard arm asks for a check that 'the uvicorn invocations in deploy/kernel.Dockerfile:197 and docker-compose.yml:144 carry no --workers greater than 1 and that no replica count exceeds 1'. That guard would PASS today while the property it exists to protect is ALREADY false. build_kernel_async is not the API's boot path alone: boltrig/api/worker.py:63 (fleet worker), boltrig/fleet/hatchet_app.py:287, boltrig/fleet/anchor.py:41 and boltrig/fleet/retention.py:30 each call it and each therefore gets its OWN InMemoryCounter. docker-compose.yml declares `kernel` (line 77) and `fleet-worker` (line 182) as separate services, and both dispatch verbs through the chokepoint where the judge verified the limiter runs (dispatch.py:448,455 enforce binding.rate_limit). Per-verb limits ARE configured today: adapters/builtin/ms_graph.py:58 (1000/min tenant), adapters/builtin/jira.py:180 (300/min), adapters/builtin/channel_send.py:101 (60/min tenant), adapters/builtin/familiar.py:107 and memory_tickets.py:56 (120/min). This falsifies the verified fact 'production currently runs a single uvicorn worker, so the per-process bound coincides with the intended bound today' (true only of the API process in isolation) and the holding's 'silently multiplies by N the day anyone adds a second worker or replica' (it already does). The 2FA (auth_routes.py:77-78) and channel-intake (channel_routes.py:66-67) surfaces the judge weighed are API-process-only, so the immateriality holding on the ALGORITHM survives unchanged.

## Disposal as implemented

- **D1, D3, D7 (the discovered breach).** `build_counter(REDIS_URL)` now exists in
  `boltrig/kernel/ratelimit.py` and `build_kernel_async` passes its result to the
  `Kernel`. A configured URL yields `RedisCounter`; no URL yields the documented
  dev fallback, which is safe because production readiness independently requires
  Redis, so a production deployment reaching the fallback is already failing its
  readiness gate loudly.
- **D3, D4.** `tests/security/test_rate_limit_backend.py` exercises the Redis
  backend against `fakeredis`, pins the wiring AND the hand-off to the Kernel,
  asserts the two backends admit and refuse the identical sequence, and asserts a
  bound survives a simulated kernel restart. Seeded-failure verified: restoring the
  pre-ruling behaviour fails two of the four.
- **D5.** The `RateLimit` dataclass docstring now states the fixed calendar window
  and the 2x boundary burst at the point of configuration, and names the evidence
  that would justify renewing the sliding-window application.
- **D6.** SEC-130 no longer asserts an unqualified "5/min trips the 6th"; FR-KER-05
  now describes the shared counter and the parity obligation.
- **D8, and the clerk's finding that it was prose-only.** The clerk was right and
  this is the repo's known failure mode: `test_the_window_is_fixed_not_sliding` was
  bound to no invariant row, so "may not be deleted without a further ruling" was
  enforceable by nothing. It is now bound to SEC-130, and deleting it fails the
  invariant gate mechanically.
- **D2** does not arise: it was conditional on the shipped counter remaining
  in-memory, and it does not. Its remedy (correcting the `docker-compose.yml`
  attribution) was applied anyway, because the comment was misleading either way.

## Two things this judgment should not be read as deciding

The unwired backend was found by the court on its own verification. It was in no
case file and neither side was heard on it, so the limbs of the ratio addressing
"an unwired or untested backend is not evidence of production behaviour" bind only
so far as an unheard point can. It was disposed of here rather than adjourned
because it was a live security defect in a shipped control, and the standing rule
is to fix those immediately rather than wait.

The clerk also observed that the refusal of a sliding window rests on the guarded
surfaces AS THEY ARE TODAY. It is refused on the evidence, and the order names
what would change it: a rate-limited surface where a single boundary burst, as
distinct from the sustained rate, causes irreversible or disproportionate harm.
