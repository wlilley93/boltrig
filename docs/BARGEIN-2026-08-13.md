# Client-side barge-in in the Tauri Worker

2026-08-13. Phase 5 of the voice plan. This document records the design, the
measurements it rests on, what was verified and how, and — importantly — one
defect that verification found and that is still open.

Status: **implemented, gates green (tsc exit 0; 87 files / 806 tests, all
passing), interrupt latency measured at a 41ms median in a real browser — and
NOT ready to ship.** Verification reproduced the one failure the whole design
exists to prevent: on a speech-shaped echo residual above about −50 dBFS, the
companion interrupts herself. See "The open defect". Do not enable this on open
speakers until that is resolved, and do not accept a headphones-only test as
evidence that it is.

**Update, 23:01, same day.** Both candidate mitigations are now implemented
behind a switch (`voiceSelfTrigger.ts`) and **neither is chosen**: the default is
still the measured-broken behaviour, because choosing needs a measurement of the
operator's real room at their real speaker volume that nobody here can make. See
"Two mitigations, one switch, no decision" and "The measurement that decides it".

## The three measured facts the design rests on

**1. The transcript is not the trigger.** Kyutai streaming STT on pocket-ears
emits its first `speech_start` 1.746s into a clip whose speech begins ~0.3s in,
because it waits for a decoded token. A companion who talks over you for 1.7s is
not doing barge-in. "Is someone talking" is a cheap question and goes on the
critical path; "what did they say" is expensive and follows behind. The
microphone keeps streaming upstream throughout an interrupt, so the transcript
arrives after the flush, not instead of it.

**2. Interrupting is a playback problem, not a generation one.** TTS runs at
roughly 10–11x realtime, so an 11s utterance is fully synthesised in under a
second. By the time a human could interrupt, generation has finished and there
is nothing left to cancel — the first barge-in test returned `{"interrupted":[]}`
for exactly this reason. The mechanism is **stop the speaker and flush the client
buffer**. `POST /interrupt` only bites past ~10s of audio; it is free, so it is
sent, but it is not the mechanism.

**3. AEC decides the playback architecture. This is the load-bearing one.**
`getUserMedia({audio:{echoCancellation, noiseSuppression, autoGainControl}})`
gives WebRTC AEC3 for free, and it works for headphones *and* open speakers. But
**AEC3 can only cancel audio the webview itself played.** TTS output must
therefore go through the page audio graph. See "The rule" at the end.

## Design

Capture graph (`VoiceCall.tsx`, one AudioContext for the call):

```
MediaStreamAudioSourceNode ──┬─> ScriptProcessorNode(4096) ─> Gain(0) ─> destination
                             └─> AnalyserNode(fftSize 512) ─┘   (barge-in tap)
```

The gate gets **its own analyser**, not a hook on `onaudioprocess`. The upload
path's ScriptProcessor buffer is 4096 frames = **85ms at 48kHz**, so a gate
quantised to it could not reach the target however it was tuned. A 512-sample
analyser spans 10.67ms and is polled every 10ms; three consecutive
above-threshold reads is 30ms of sustained speech. The analyser rides the
existing gain-0 keep-alive, so the microphone is never audible.

Playback graph:

```
AudioBufferSourceNode(×N, scheduled ahead via playAt) ─> AnalyserNode(1024) ─> destination
```

On trigger:

1. `stopQueuedPlayback` — stops every scheduled source, clears
   `playbackSources`, resets `playAt` to `currentTime`.
2. `requestSelfHostedInterrupt` — fire-and-forget `POST /interrupt`, only when
   `VITE_SELF_HOSTED_TTS_ORIGIN` is set (unset by default; the Worker never
   guesses a local port).
3. **Inbound PCM is dropped for 600ms** (refreshed while the user is still
   talking, hard-capped at 2500ms). This is not in the original plan and is
   necessary: the provider has not stopped generating the turn that was talked
   over, so PCM keeps arriving and would be scheduled straight behind the audio
   just stopped. The cap exists so a provider that never confirms cannot mute the
   companion indefinitely.

Self-trigger guard, two parts: an 18dB margin over a separately-tracked *echo*
floor while she is speaking (vs 12dB over the room floor when she is not), and a
200ms settling window at the start of each turn during which the gate cannot
fire at all. Plus a 500ms warm-up, a 400ms cooldown, and no observation while
muted. **This is the part that does not work** — see "The open defect" — and the
two replacements for it are behind the switch in `voiceSelfTrigger.ts`, off by
default. Both add a second reading to each frame:

```
AudioBufferSourceNode(×N) ─> AnalyserNode(1024) ─> destination
                                    └─> the gate's reference: what she is emitting
```

### Playback is in the page graph, not native (fact 3 satisfied)

Verified from source, both directions:

- **Nothing plays audio on the Rust side.** `src-tauri/Cargo.toml` has no
  `rodio`, `cpal`, `coreaudio`, `symphonia` or any audio dependency. A grep for
  `AudioUnit|AVAudio|AudioQueue|coreaudio|rodio|cpal` across `src-tauri/src/**`
  returns **0 hits**. All 34 `#[tauri::command]`s are account, api-proxy, camera,
  device-agent, update and roots. Contrast with the **camera**, which *is* native
  (`camerad`, `camera_uvc.m`) — audio deliberately is not, and must not be made
  to match it.
- **The whole Worker has exactly one AudioContext and one getUserMedia**, both in
  `VoiceCall.tsx` (`:620`, `:609`). No `new Audio(`, no `<audio>`, no
  `MediaRecorder`, no `speechSynthesis` anywhere in `apps/worker/src`.

The playback path itself (`VoiceCall.tsx:1650`, `playPcm`):

```ts
const buffer = context.createBuffer(1, pcm.length, 24_000);
const source = context.createBufferSource();
source.buffer = buffer;
source.connect(media.analyser ?? context.destination);
media.playbackSources.add(source);
const startsAt = Math.max(context.currentTime, playAt.current);
source.start(startsAt);
playAt.current = startsAt + buffer.duration;
```

Decoded from binary WebSocket frames, scheduled ahead of wall clock into
`context.destination`. That is the webview's own output, which is what gives AEC3
its reference signal.

### Latency: measured, in a real browser

**Method.** The real shipped modules (`voiceBargeIn.ts`, `voiceBargeInGraph.ts`)
were bundled unmodified with vite and loaded into a page in real Chromium. The
page builds a synthetic microphone signal at the context's 48kHz — white noise at
−60 dBFS (the measured inter-word floor of the real captures), plus a synthetic
AEC residual of the companion's audio, plus **real recorded speech** from
`/tmp/bargein.wav` trimmed to its first voiced sample and scaled to −26 dBFS (its
measured median voiced level), inserted at a known offset. The real
`attachBargeInCapture` and `startBargeInGate` drive the real gate. Companion
audio is fed in 100ms chunks through a mirror of `playPcm`. An `AudioWorklet` on
the playback bus reports the audio-clock time of the last render quantum
(128 frames = 2.67ms) carrying a non-zero sample.

Latency = (last non-silent quantum on the playback bus) − (user speech onset),
computed entirely on the audio clock.

**Result, 20 trials, onset staggered by 5.3ms to sample setInterval phase:**

| | ms |
| --- | --- |
| min | 35.8 |
| median | **41.0** |
| mean | 41.8 |
| max | 46.6 |

Fired in 20/20. In 19 of 20 the audio stopped in the same quantum the gate fired,
i.e. `source.stop()` took effect within one render quantum. This matches the
predicted decomposition: ~10.7ms to fill the analyser window + 3 × 10ms polls
≈ 40ms. **The plan's ~50ms target is met** in this regime.

**What this number does and does not include.** It includes the analyser window,
`setInterval` jitter, the gate, and the time for `stop()` to silence the bus. It
**excludes** microphone hardware and OS capture latency, and AEC3 processing
delay, because there was no usable microphone. Add those for a real-world figure.
Two further caveats: the headless audio clock ran at ~0.93–0.97 of wall clock, so
poll spacing in audio-time is slightly compressed; and the microphone signal is
synthetic apart from the speech waveform itself.

## The open defect: the companion self-triggers on her own voice

This is the failure the design exists to prevent, and **it reproduces**.

With the user silent and only the companion's AEC residual in the microphone, the
gate fires on her own audio, typically 0.3–1.0s into the turn — just after the
200ms settling window expires. Rate over 6 trials per level, speech-shaped
residual:

| AEC residual (RMS) | self-triggered |
| --- | --- |
| −60 dBFS | 0/6 |
| −55 dBFS | 0/6 |
| −52 dBFS | 0/6 |
| −50 dBFS | **5/6** |
| −48 dBFS | **6/6** |
| −45 dBFS | **6/6** |
| −40 dBFS | **6/6** |

**Diagnosis, confirmed by experiment.** The same test with a *stationary* residual
— steady noise at the same RMS — never triggers, even at −30 dBFS (0/4 at −45,
−40 and −30). Only the speech-shaped residual triggers (4/4 at all three). The
adaptive floor uses fast-down/slow-up tracking, which is correct for stationary
room noise and wrong for the residual of *speech*, which is highly non-stationary.
The floor sinks into the gaps between the companion's words, and her next syllable
then reads as a large positive onset above it.

Note also where the boundary sits: `BARGE_IN_MIN_RMS = 0.004` is −47.96 dBFS. The
guard that actually holds below −52 dBFS is the **absolute backstop**, not the
18dB echo margin. The echo-margin machinery is doing much less work than the code
comments claim.

**Is −50 dBFS residual realistic?** AEC3 typically achieves 20–40dB of echo return
loss enhancement. A speaker arriving at the microphone at −20 dBFS with 25dB ERLE
leaves −45 dBFS — inside the failing band. On headphones the residual is far
lower and the defect vanishes, which is exactly why this is easy to ship broken.

## Two mitigations, one switch, no decision

Both candidates are implemented. **Neither is on.** `echo-floor` — today's
behaviour, the one measured above — is still the default, and the switch has to
be thrown deliberately.

That is not fence-sitting. Both mitigations are parameterised by *echo coupling*:
how far below the playback bus the companion's residual arrives at the
microphone. That number is not a property of the code. It is a property of the
operator's speaker volume, their room, their microphone and AGC, and it is the
one number nobody in this session could measure, because Chrome for Testing has
no macOS Microphone grant and denial arrives as digital silence rather than as an
error. Picking a default from a room nobody heard is exactly the mistake the plan
warns about, and it would be indistinguishable from a fix until a user on
speakers found it.

Both stop guessing at the residual and use the reference signal the page already
has. The playback bus carries the companion's audio and nothing else, so its
level is exactly what AEC3 is being asked to cancel.

### a) `reference-margin` — the bar rises with her own voice

Peak-hold the playback bus (instant attack, 24 dB/s release) and require the
microphone to clear `envelope + couplingDb + marginDb`. Her leakage cannot clear
that bar however modulated it is, because the bar is made of the same modulation.
The slow release is the whole point: unlike the floor tracker, the bar must not
sink into the gaps between her words, and 24 dB/s falls only 2.4 dB across a
100ms gap — while the residual that gap contains has vanished with the syllable
that caused it.

**Latency: unchanged.** The gate still trips on the third consecutive hot frame.

### b) `playback-hangover` — deaf while she is audible

Block the gate outright whenever the playback bus is above
`hangoverReferenceDb`, plus a trailing `hangoverMs` to cover speaker-to-mic
flight time, AEC3's own delay and room decay. The user is heard in the gaps
between her words. Immune by construction — it does not care what the coupling
is, because it never compares levels at all.

**Latency: it costs the wait for her next gap.** And the gate needs a gap longer
than `hangoverMs` plus three frames, so with the default 80ms hangover a speaker
who pauses only 60ms between words cannot be interrupted at all until she
finishes a phrase.

### The switch, and how to tune it

`localStorage` first, then the build-time environment, then the default — so the
room can be measured without a rebuild, which is the only way the procedure below
is practical to run.

| what | localStorage key | env var | default |
| --- | --- | --- | --- |
| mode | `boltrig.bargeIn.mode` | `VITE_BARGE_IN_SELF_TRIGGER_MODE` | `echo-floor` |
| echo coupling, dB | `boltrig.bargeIn.couplingDb` | `VITE_BARGE_IN_ECHO_COUPLING_DB` | `-20` |
| margin over it, dB | `boltrig.bargeIn.marginDb` | `VITE_BARGE_IN_REFERENCE_MARGIN_DB` | `6` |
| bar release, dB/s | `boltrig.bargeIn.releaseDbPerSecond` | `VITE_BARGE_IN_REFERENCE_RELEASE_DB_PER_S` | `24` |
| hangover, ms | `boltrig.bargeIn.hangoverMs` | `VITE_BARGE_IN_HANGOVER_MS` | `80` |
| hangover threshold, dBFS | `boltrig.bargeIn.hangoverReferenceDb` | `VITE_BARGE_IN_HANGOVER_REFERENCE_DB` | `-45` |
| per-frame diagnostics | `boltrig.bargeIn.diagnostics` | `VITE_BARGE_IN_DIAGNOSTICS` | off |

```js
localStorage.setItem("boltrig.bargeIn.mode", "reference-margin");  // then rejoin the call
```

A value that is not one of the three modes, or not a finite number, is ignored
rather than guessed at. Tuning is read once, when the call's gate is built, so
changes take effect on the next call rather than mid-sentence.

### What the mitigations do to the *modelled* signal

Not a room. This is the same class of synthetic signal that produced the table
above, driven through the real `startBargeInGate` poll at 10ms frames:
her bus at −20 dBFS in 120ms syllables with 120ms gaps, −20 dB coupling
(so −40 dBFS of residual — the level that self-triggered 6/6), room floor
−61 dBFS, user speech −26 dBFS.

| mode | self-interrupts in 3s of her turn | first one | user's barge-in detected after |
| --- | --- | --- | --- |
| `echo-floor` | **6** (one per cooldown) | 260ms into the turn | 20ms |
| `reference-margin` | 0 | — | 20ms |
| `playback-hangover` | 0 | — | 170ms; **never**, if her gaps are 60ms |

Both mitigations also held when the model was made much worse than the
measurement: `reference-margin` at −6 dB coupling (0 self-interrupts, because the
bar is relative) and `playback-hangover` at 0 dB coupling (0, because it never
compares levels). The stationary-residual control still fires nothing in any
mode, as it did in the original experiment.

The 20ms and 170ms are model frames, not wall clock: add the analyser window and
poll jitter that the browser harness measured as a 41ms median. `echo-floor` and
`reference-margin` share a trigger path, so the 41ms figure carries over
unchanged; `playback-hangover` adds roughly 130–160ms on this speech pattern and
is unbounded on a speaker who does not pause.

### Expectation, honestly held

**`reference-margin` should win, and I would be surprised to be wrong — but I
have not heard the room.** Three reasons:

1. **It keeps the latency the design was built for.** 41ms median, 20/20 fired.
   `playback-hangover` cannot; on this speech pattern it lands near 200ms, and
   the brief's own bar is that a fix pushing past ~80ms is not a fix.
2. **Its failure mode is graceful and tunable.** If `couplingDb` is set too
   pessimistically the bar is a little high and a quiet interruption is missed
   until the user speaks up; if set too optimistically the old self-trigger
   returns and the diagnostic shows exactly why. `playback-hangover` fails by
   going silently deaf for whole phrases, which reads to the user as "she does
   not listen" and produces no signal to debug from.
3. **The reference is exact.** It is the same buffer the webview hands the
   speaker, and the same signal AEC3 uses. Only the acoustic path between them is
   uncertain, and that is one scalar, which is measurable.

What would change my mind: a room where the coupling **varies a lot within a
turn** — a laptop speaker driven into compression, an AGC that pumps, a
microphone that moves. `reference-margin` assumes one scalar coupling; if the
real one swings 15 dB inside a sentence, no single `couplingDb` is both safe and
sensitive, and `playback-hangover`'s indifference to level becomes the right
trade. The diagnostic below measures that spread directly, so the choice does not
have to be made on taste.

## The measurement that decides it

**On open speakers. Headphones hide this entirely and a green headphones test
proves nothing** — the residual there is tens of dB lower and every mode passes.

Run it in the Worker with a real call, at the volume actually used.

1. **Turn the diagnostic on and rejoin the call.**

   ```js
   localStorage.setItem("boltrig.bargeIn.diagnostics", "1");
   ```

2. **Collect frames.** Paste this before she speaks; it listens to the gate's own
   per-frame event, which carries both levels and nothing else:

   ```js
   const rows = [];
   addEventListener("boltrig:barge-in-frame", (e) => rows.push(e.detail));
   const db = (x) => 20 * Math.log10(Math.max(x, 1e-9));
   const report = () => {
     const hers = rows.filter((r) => r.playing && db(r.reference) > -45);
     const coupling = hers.map((r) => db(r.rms) - db(r.reference)).sort((a, b) => a - b);
     const at = (q) => coupling[Math.min(coupling.length - 1, Math.floor(coupling.length * q))];
     console.table({
       frames: hers.length,
       "coupling p50 dB": at(0.5)?.toFixed(1),
       "coupling p95 dB": at(0.95)?.toFixed(1),
       "worst dB": at(1)?.toFixed(1),
       "spread p50→p95 dB": (at(0.95) - at(0.5)).toFixed(1),
       "self-interrupts": rows.filter((r) => r.trigger).length,
     });
   };
   ```

3. **Ask her a question that gets a long answer, and say nothing at all.** Let her
   run 20–30 seconds. Then `report()`.

   - `self-interrupts` **must be 0**. In `echo-floor` it will not be, and that is
     the defect reproducing in your room rather than in a model.
   - `coupling p95` is the number to put in `boltrig.bargeIn.couplingDb`. Use p95,
     not p50 — the bar has to clear the loud excursions, not the average.
   - `spread p50→p95` is what decides between the two modes. Under ~10 dB,
     `reference-margin`. Much more than that and one scalar cannot cover the
     turn; prefer `playback-hangover` and tune `hangoverMs` up until the
     self-interrupts stop.

4. **Now interrupt her**, five or six times, at different points in a sentence —
   some mid-word, some in a gap. Every attempt should stop her. Count the ones
   that do not, and how long the ones that do took to bite by ear.

5. **Repeat both halves at your loudest realistic volume**, and once with the
   microphone moved (a laptop lid angle changes coupling by more than people
   expect).

6. **Write the numbers into this document** — the coupling, the spread, the mode
   chosen, the volume and the room. A tuning constant with no recorded room is
   the same problem again, one session later.

Only after that should the default in `voiceSelfTrigger.ts` change from
`echo-floor`, and it should change to the mode the measurement chose, in the same
commit as the measurement.

## What needs a human at a real microphone with open speakers

None of the following can be settled headless, and the first is the one that
matters:

1. **Whether the companion self-triggers on open speakers.** The synthetic test
   above says she will if AEC3 leaves more than about −52 dBFS of residual, but
   only a real room can say what AEC3 actually leaves at your speaker volume, your
   room, your microphone. **Test on open speakers, not headphones** — headphones
   make the problem vanish and would hide the defect completely. This is now a
   written procedure with a diagnostic behind it: see "The measurement that
   decides it". It is also the thing that picks which mitigation ships.
2. **The real end-to-end latency**, including microphone hardware and AEC3 delay.
   The 41ms median above excludes both.
3. **Whether the room's noise floor sits where the thresholds assume.** −60 dBFS
   came from TTS renders, not from a microphone through AEC + NS + AGC. AGC in
   particular will move the floor around.
4. **Whether 400ms cooldown and 600ms drop window feel right by ear.** These are
   comfort parameters and no test can judge them.
5. **The plan's own Phase 5 check** — speak an 11s line, talk over it at 2s,
   confirm the audio stops and the microphone did not transcribe the companion —
   has never been run against live pocket-voice and pocket-ears.

## The rule

**TTS playback must never move to the Rust side without moving AEC with it.**

AEC3 lives inside the webview's audio pipeline and can only cancel what the
webview itself played. If playback moves to a native Rust path — `rodio`, `cpal`,
an AVFoundation player, anything — the canceller loses its reference signal and
the echo returns in full. The microphone then hears the companion, the gate reads
her as the user, playback stops mid-sentence, the STT transcribes her own words
back as user input, and she interrupts herself in a loop.

This will look fine on headphones. It will be discovered by a user on speakers.

The camera in this app *is* native, and that asymmetry is deliberate. Do not let a
later change tidy audio into matching it.

## Other constraints observed

- **The Tauri CSP does not allow the pocket services.** `connect-src` in both
  `csp` and `devCsp` (`src-tauri/tauri.conf.json`) lists only `'self'`, the
  boltrig.io origins, and — in dev only — `http://localhost:* ws://localhost:*`.
  `http://127.0.0.1:8911` and `ws://127.0.0.1:8912` match neither, since
  `localhost` and `127.0.0.1` are distinct CSP source expressions. Nothing is
  broken today because `VITE_SELF_HOSTED_TTS_ORIGIN` is unset by default and the
  `/interrupt` POST is therefore never attempted. Setting it requires widening
  the CSP first.
- The Rust proxy is not a way around this: `desktop_api_request` is pinned to the
  device session's `api_origin`, and the transport whitelists response headers to
  `content-type, content-length, content-disposition, etag`, so pocket-voice's
  `X-Audio-Seconds` / `X-Realtime-Factor` would be stripped.
- pocket-voice and pocket-ears remain bound to loopback. No listener was added,
  no tailscale serve mount touched. (A temporary `127.0.0.1` static server was
  used for the browser harness and shut down afterwards.)
- Nothing was committed.
- The mitigation pass added no listener either. The capture runner started its
